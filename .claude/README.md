# AI 協作資產的設計說明

這個目錄把專案的架構約束與操作流程，沉澱成 AI 協作時可自動生效的資產。
目的不是「讓 AI 更聰明」，而是**讓正確的做法變成預設路徑，讓錯誤的做法需要刻意繞過**。

---

## 四種載體的選用原則

決定一件知識該放哪裡，只需要問兩個問題：
**它多久用得到一次？** 以及 **它能不能被機器判定？**

| 載體 | 何時載入 | 適合放什麼 | 判斷準則 |
|------|----------|------------|----------|
| **Instructions**（`CLAUDE.md`） | 每次對話 | 違反就會出事的鐵則 | 「幾乎每次改動都要遵守」 |
| **Skills**（`.claude/skills/`） | 任務相關時 | 多步驟的標準流程與檢查清單 | 「只有做這類任務時才需要」 |
| **Hooks**（`.claude/hooks/`） | 工具事件觸發 | 能被程式判定的違規 | 「規則能寫成 grep 或 AST 檢查」 |
| **Agents**（`.claude/agents/`） | 明確委派時 | 需要獨立脈絡的深度審查 | 「需要通讀多個檔案才能下判斷」 |

### 為什麼不全部塞進 CLAUDE.md？

因為每次對話都會載入它。塞進去的每一行都在稀釋真正重要的規則——
一份 500 行的指南，實際效果反而不如 80 行的精簡版。

**判斷標準是頻率**：分層規則幾乎每次改動都適用 → Instructions；
壓測流程一個月用一次 → Skill。

### 為什麼有 Hook 還要有 Instructions？

兩者的**失效模式不同**，是互補而非重複：

- Instructions 靠模型自律，可能被長對話稀釋，但能涵蓋無法被程式判定的規則
  （例如「註解要寫為什麼」）
- Hook 是確定性的，一定會執行，但只能檢查可被機器判定的模式
  （例如「domain 模組不得 import spring」）

架構分層兩邊都有，因為它同時具備「重要」與「可判定」兩個性質，
值得用兩層防護——一層失效還有另一層。

## 目錄內容

### Instructions — [`../CLAUDE.md`](../CLAUDE.md)

7 條鐵則：分層依賴、熱路徑禁忌、庫存一致性、三層冪等、Lua 契約、
交易自我呼叫陷阱、時鐘注入。加上程式碼慣例與常用指令。

刻意控制在能一眼讀完的長度。**新增規則前先問：這條規則是不是幾乎每次改動都用得到？**
不是的話，它屬於 Skill。

### Skills — [`skills/`](skills/)

| Skill | 觸發時機 | 解決什麼問題 |
|-------|----------|--------------|
| `seckill-lua-script` | 新增或修改 Lua 腳本 | Lua 回傳碼與 Java 列舉、測試三方同步；hash tag 規則 |
| `add-use-case` | 新增業務功能 | Port → Service → Adapter → Test 的正確順序與檢查清單 |
| `add-domain-event` | 新增領域事件 | Outbox 寫入時機、消費端冪等、DLQ 補償的完整鏈路 |
| `seckill-load-test` | 壓測與容量規劃 | 壓測腳本、該看哪些指標、如何判讀瓶頸位置 |
| `oversell-incident` | 超賣／少賣事故 | 排查順序、止血手段、根因定位的 runbook |
| `review-changes` | Review 改動、開 PR 前自我檢查 | 格式與註解的機械檢查腳本＋人工判斷清單；並標明哪些檢查已由 hooks 與 agents 涵蓋 |

每個 Skill 都包含**檢查清單**與**常見錯誤**——後者往往比前者更有價值，
因為那是真正會出錯的地方。

`review-changes` 是唯一附帶可執行腳本的 skill
（[`check_style.py`](skills/review-changes/check_style.py)）。

> 名稱刻意避開 `code-review`——那是 Claude Code 內建指令的名字，
> 同名會讓「要跑哪一個」變得不確定。
它刻意**不**掛進 PostToolUse hook：格式問題不該在寫到一半時打斷思路，
那是 review 階段的事。hooks 只留給「會出事」的違規。

### Hooks — [`hooks/`](hooks/)

| Hook | 觸發 | 行為 |
|------|------|------|
| `check_layering.py` | 寫入 `.java` 後 | 領域層／應用層出現禁用 import 時**阻擋並說明原因** |
| `check_lua_contract.py` | 寫入 `.lua` 或 `StockDeductionOutcome` 後 | 提醒同步另外兩處，並列出必跑的測試 |
| `remind_tests.py` | 對話結束時 | 若本次改到併發相關檔案，提醒執行對應測試 |

設計原則：

1. **Hook 必須快**（< 200ms）。它在每次存檔時執行，慢一點就會讓整個流程變得難以忍受。
   因此這些 hook 都是純文字檢查，不編譯、不啟動 JVM。
2. **只擋能確定的違規**。誤報比漏報更傷——被誤擋幾次之後，人就會想辦法關掉它。
3. **阻擋時必須說明「為什麼」與「怎麼改」**，而不只是「不允許」。

### Agents — [`agents/`](agents/)

| Agent | 職責 |
|-------|------|
| `concurrency-reviewer` | 併發正確性審查：超賣路徑、冪等性、鎖的必要性、交易邊界 |
| `hotpath-auditor` | 熱路徑效能審查：額外 RTT、阻塞呼叫、快取失效風險 |

做成 Agent 而非 Skill 的理由：這兩類審查需要**同時讀懂多個檔案的互動**
（Lua 腳本 + Repository + Service + 測試），會產生大量中間脈絡。
放進主對話會把上下文塞滿，交給子代理則只回傳結論。

## 使用方式

Skills 會依描述自動觸發，也可直接指名：

```
/seckill-lua-script      改 Lua 腳本前先載入流程
/oversell-incident       線上疑似超賣時的排查步驟
```

Agents 需明確委派：

```
用 concurrency-reviewer 檢查我這次的改動有沒有併發問題
```

Hooks 會自動生效，設定在 [`settings.json`](settings.json)。

## 維護原則

**這些資產和程式碼一樣會腐化。** 三個檢查點：

1. 改了架構規則 → 同步更新 `CLAUDE.md` 與 `check_layering.py` 的禁用清單
2. 某條 Skill 連續幾個月沒用到 → 考慮刪掉，過期的流程比沒有流程更危險
3. Hook 開始頻繁誤報 → 立刻修正或移除，不要留著讓人習慣性忽略
