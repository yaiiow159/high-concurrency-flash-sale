# 程式碼審查

這個專案已經有三道自動防線。**審查的價值在於它們抓不到的東西**——
把時間花在重複機器已經做過的檢查上，等於沒有審查。

| 防線 | 涵蓋範圍 | 時機 |
|------|----------|------|
| `.claude/hooks/` | 分層違規、熱路徑禁忌、Lua 契約 | 存檔當下，違規直接擋下 |
| `check_style.py` | 格式、簡體字、複述型註解、Clock 繞過 | review 時執行 |
| `concurrency-reviewer` / `hotpath-auditor` agent | 併發正確性、尖峰效能 | 改動涉及庫存或熱路徑時委派 |
| **本清單** | 判斷題：註解說了什麼、快照還是引用、測試抓不抓得到迴歸 | 只能靠讀 |

---

## 步驟一：跑機械檢查

```bash
python .claude/skills/code-review/check_style.py
```

預設檢查未提交的改動。`--all` 檢查整個專案，也可以直接指定檔案。

這支腳本只檢查**能被機器明確判定**的事：行長、tab、行尾空白、
註解裡的簡體字、複述型註解、領域層直接呼叫 `Instant.now()`、
新增自訂例外類別、領域型別缺 Javadoc、遺留的 TODO。

> **它刻意不掛進 PostToolUse hook。** 格式問題不該在寫到一半時打斷思路——
> 那是 review 階段的事。hooks 只留給「會出事」的違規。

字表的維護方式寫在腳本註解裡：**不要憑印象加字**。
手打過兩次，兩次都混進「作」「只」「量」這種兩邊同形的字，
讓檢查變成誤報機器。正確作法是拿現有程式碼（全繁體）當驗收集。

---

## 步驟二：委派專門的 agent

改動若涉及以下範圍，**先委派再自己讀**——這兩個 agent 的判準比通用審查嚴格得多：

| 改動涉及 | 委派給 |
|----------|--------|
| 庫存扣減、Lua、MQ 消費端、分散式鎖、交易邊界、補償 | `concurrency-reviewer` |
| `SeckillApplicationService`、`RedisStockRepository`、多級快取、Controller | `hotpath-auditor` |

## 步驟三：人工審查清單

以下每一條都**無法被機器判定**，只能靠讀。

### 註解

專案規則是「註解寫為什麼，不寫做了什麼」。實際審查時問三個問題：

- **刪掉這行註解，讀者會失去什麼？** 答不出來就該刪。
  `// 迴圈遍歷訂單` 是雜訊；
  `// 逐筆處理而非批次 UPDATE，因為批次會繞過聚合根的狀態機` 才有價值。
- **它解釋的是「不明顯的取捨」還是「明顯的語法」？**
  好的註解通常在回答「為什麼不用更直覺的那個做法」。
- **這個決定被推翻時，註解會不會變成謊言？**
  會的話，把它移到更靠近決定的地方，或改寫成不會過期的說法。

**特別注意反直覺的程式碼一定要有註解。**這個專案裡到處是
「看起來多餘、其實是防線」的寫法：`RefreshTokenRevoker` 為什麼要獨立成一個 Bean、
劃撥為什麼一定先動 MySQL、對帳為什麼不自動修。這些少了註解，
下一個人會「順手簡化掉」，而簡化的後果要幾個月後對帳才看得出來。

Javadoc 與註解一律**繁體中文**，識別符號一律英文。

### 命名與型別

- 裸 `String` / `Long` 當識別碼傳遞 → 應該是值物件（見 `OrderNo`、`Email`）。
  值物件的價值是讓編譯器擋下參數傳錯，而不是為了包裝而包裝。
- 布林參數（`doSomething(true)`）→ 呼叫端讀不出那個 `true` 是什麼意思，
  改成列舉或拆成兩個方法。
- 方法名說的事和它實際做的事是否一致？特別是有副作用的 getter。

### 快照 vs 引用（**最容易做錯的一類**）

訂單裡的任何欄位，問一句：**「這個值日後被改掉，這張訂單該不該跟著變？」**

不該的話它就必須是快照，不能是 ID 引用：

| 欄位 | 為什麼是快照 |
|------|--------------|
| `OrderLine.skuSnapshot` / `unitPrice` | 商家改名或調價，歷史訂單不能跟著變 |
| `Order.shippingInfo` | 使用者搬家，三個月前已送達的訂單不能顯示成寄到新家 |
| `Order.totalAmount` | 反正規化，前提是建立後不可變 |

對應的 `OrderEntity` 欄位必須是 `updatable = false`。那不是裝飾。

### 界限脈絡

**ArchUnit 只管分層（api → infrastructure → application → domain），
抓不到脈絡之間的耦合。** 只能靠 review：

- `domain/identity/` 的類別 import 了 `domain/order/` 的型別嗎？
  （做過一次：`Address.snapshot()` 回傳 `ShippingInfo`，把兩個脈絡黏死，
  後來改成應用層轉換。）
- 跨脈絡的轉換應該放在應用層——那本來就是負責編排的地方。
- 為了避免耦合而產生的少量重複（例如地址格式化各有一份）是可以接受的代價。

### 通道紀律

`order.channel()` **只用於追溯與報表，不可用於控制流程**（ADR-0006）。

領域層一旦出現 `if (channel == SECKILL)`，兩條通道的差異就滲透進共用部分。
需要分歧時，判斷依據應該是**更精確的事實**：
例如關單退庫看的是 `line.sourceActivityId()` 是否為 null，
那是「這批貨從哪個池子扣的」，而不是「這張訂單是誰建的」。

### 交易邊界

- `@Transactional` 方法被同一個 Bean 內部呼叫嗎？**會安靜失效**（規則 6）。
  參考 `OutboxRelayScheduler` / `OutboxRelayer` 的拆分。
- 交易裡有 Redis、HTTP、Kafka 呼叫嗎？它們不會跟著回滾。
- **預期中的失敗有沒有用拋例外表達？** 在交易內拋未受檢例外會把整個交易
  標記成 rollback-only，就算上層捕捉掉也救不回來，最後炸在 commit。
  「售罄」是預期結果，應該回傳結果物件；「同一張訂單被扣兩次」才該拋。

### 錯誤處理

- 新增 `ErrorCode` 時，`GlobalExceptionHandler.STATUS_MAPPING` 有沒有補上對應？
  沒補的話會落到預設狀態碼，而前端往往靠狀態碼分流。
- 「查不到」與「無權限」是否都回 404？回 403 等於確認那個 ID 有效，
  讓攻擊者能靠窮舉列舉資源。
- 例外訊息會不會洩漏個資或內部結構？

### 測試

**最重要的一條：這個測試真的抓得到它要防的迴歸嗎？**

驗證方法是把修正暫時還原，確認測試會失敗。這個專案有兩次教訓：

- refresh token 重用偵測的 mock 測試看到 `revokeFamily` 被呼叫就判定通過，
  但那個撤銷其實被外層交易回滾掉了——測試全綠，功能完全失效。
- 單一 SKU 對帳回全零的 bug，加了回歸測試後實際還原修正驗證，
  確認會失敗（`expected: 4000`）才算數。

其餘：

- 測試名稱說的是「行為與理由」還是「方法名」？
  `rejectsNonPositiveLineQuantity` 不如
  `@DisplayName("行數量必須為正——否則會變成庫存回補漏洞")`。
- 併發相關的改動有沒有真正的併發測試（`CountDownLatch` 同時放行）？
- 有沒有測到「什麼情況絕不自動修」這類**反向規則**？那些最容易在日後被放寬。

### 資料庫遷移

- 新欄位對既有資料是否安全（NOT NULL 有沒有預設值）？
- 遷移有沒有讓**舊資料在新規則下也成立**？只把表建出來不算完成——
  V7 補了既有活動的劃撥流水，否則對帳每一輪都會報不平。
- 唯一索引的欄位組合想清楚了嗎？
  （`(ref_type, ref_no, type)` 少了 `sku_id`，多品項訂單的第二行就會被擋下。）
- 索引是否對應實際的查詢條件？

### 前端

- 個資或身分狀態有沒有進到會被 ISR 快取的 SSR HTML？
  訂單頁與地址頁必須 `isr: false`——這不是效能取捨，是安全邊界。
- access token 只能在記憶體，不可進 localStorage。
- 手寫的 `types/api.ts` 有沒有跟著後端改？**這裡漂移過兩次**
  （`productId` → `skuId`；`OrderView` 與 `OrderDetailView` 兩份描述同一個回應）。
- 冪等鍵是在送出前產生並保留、只在成功後才作廢嗎？
  每次重試都換新值的話，使用者按兩次就會買到兩份。

## 步驟四：跑測試

```bash
mvn test                                              # 全部（需 Docker）
mvn test -pl flash-sale-domain,flash-sale-application # 快速回饋，不需 Docker
```

改動涉及 Lua、`StockRepository` 或任何併發程式碼時，
**`RedisStockRepositoryTest` 必須跑過**——那是防超賣的唯一實證。

> 用 `-pl <module>` 單獨跑某個模組時要加 `-am`，
> 否則它會去 `~/.m2` 拿舊的 jar，出現「找不到剛新增的類別」這種假錯誤。

## 輸出格式

審查結論按**嚴重度**排序，每一條都要能回答「這會怎麼出事」：

```
🔴 會出事
   路徑:行號  問題
   後果：具體的失敗情境（什麼輸入 → 什麼錯誤結果）

🟠 會慢慢腐蝕
   路徑:行號  問題
   理由：為什麼現在不痛，之後會痛

🟡 可以更好
   路徑:行號  建議
```

**沒有問題就說沒有問題。** 為了顯得認真而湊出幾條無關痛癢的建議，
會讓真正重要的那一條被淹沒——這與對帳只在異常時輸出日誌是同一個道理。
