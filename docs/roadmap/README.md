# 電商平台演進規劃

把現有的秒殺引擎擴充成完整電商平台的路線圖。

> **這份文件的前提**：作品集導向，目標是「架構決策的深度」而非「功能的廣度」。
> 每個項目都標了 `[展示]`（技術亮點）或 `[必要]`（少了就不成立）——
> 若目標轉為真實營運，把 `[必要]` 全部前移即可重排優先序。
>
> 工時估算假設：**一人開發、每週 15–20 小時**。

## 一、現況盤點

### 已經有的

| 面向 | 現況 |
|------|------|
| 架構 | 六角架構模組化單體，4 模組，ArchUnit 強制分層 |
| 秒殺 | 四層削峰漏斗、Redis Lua 原子扣減、防超賣已實證 |
| 一致性 | Outbox + Saga 補償、三層冪等、庫存對帳 |
| 認證 | OAuth2 Resource Server + JWT |
| 可觀測性 | Micrometer + Prometheus + Grafana，9 條告警 |
| 測試 | 70 支（含 1000 執行緒防超賣） |
| 決策記錄 | 5 份 ADR |

### 還沒有的

資料庫只有 **3 張表**（`seckill_activity`、`seckill_order`、`outbox_event`）。
以電商平台的標準看，缺口是結構性的：

| 缺口 | 現況 | 嚴重度 |
|------|------|--------|
| **商品目錄** | 只有活動裡的 `productId` + 商品名快照，沒有商品實體 | 🔴 阻斷性 |
| **多品項訂單** | `SeckillOrder` 是單品項單活動，購物車結帳寫不進去 | 🔴 阻斷性 |
| **一般庫存** | 只有秒殺的 Redis 預熱庫存，一般商品無處扣減 | 🔴 阻斷性 |
| **付款** | 訂單停在 `PENDING_PAYMENT`，沒有任何東西能讓它變 `PAID` | 🔴 阻斷性 |
| **使用者實體** | 只有 JWT 的 `sub`，沒有會員資料、沒有收貨地址 | 🟠 高 |
| **Refresh token** | 令牌 2 小時過期就得重登，前端無法接受 | 🟠 高 |
| 購物車 | 無 | 🟠 高 |
| 退款退貨 | `OrderStatus` 只有 4 態，無退款路徑 | 🟡 中 |
| 履約物流 | 無 | 🟡 中 |
| 促銷優惠 | 無 | 🟡 中 |
| 搜尋 | 無 | 🟡 中 |
| 評價 | 無 | 🟢 低 |
| 營運後台 | 只有一個預熱端點 | 🟡 中 |
| 前端 | 無 | 🟠 高 |

## 二、核心架構主張

規劃的每個決定都從這五條推導出來。**先讀完這節，後面的階段安排才會有道理。**

### 主張 1：秒殺是特例通道，不是骨幹

這是整份規劃最重要的一條。

現有架構的**每一個設計**都建立在同一個前提上：
**流量極大、庫存極小、99.9% 的請求注定失敗**。

- 本機售罄標記 → 因為絕大多數請求會失敗
- 非同步下單（202 + 輪詢）→ 因為要把 DB 寫入移出熱路徑
- 庫存放 Redis → 因為所有請求競爭同一行資料
- 熱路徑禁 DB → 因為 DB 是吞吐瓶頸

**一般電商的流量特徵完全相反**：流量正常、SKU 數以萬計、絕大多數請求會成功、
領域規則複雜（優惠、稅、運費）、需要立即的交易一致性。

把一般下單也塞進秒殺通道會發生什麼：

| 秒殺的設計 | 套到一般下單的後果 |
|---|---|
| 非同步 202 + 輪詢 | 使用者按下「結帳」後要輪詢才知道買到沒——體驗災難 |
| 庫存預熱進 Redis | 五萬個 SKU 全部預熱？記憶體與預熱時間都不可行 |
| Lua 原子扣減 | 多品項 + 優惠券 + 運費計算，Lua 寫不下也不該寫 |
| 本機售罄標記 | 一般商品不會售罄，這層純粹是額外複雜度 |

**因此：兩條下單通道。**

```
                    ┌─────────────────────────────────┐
                    │  共用：使用者 · 商品 · 地址      │
                    │        付款 · 履約 · 通知        │
                    └───────────┬─────────────────────┘
                                │
              ┌─────────────────┴─────────────────┐
              │                                   │
    ┌─────────▼──────────┐            ┌──────────▼─────────┐
    │   一般下單通道      │            │   秒殺下單通道      │
    │                    │            │                    │
    │  同步、交易一致     │            │  非同步、最終一致   │
    │  DB 樂觀鎖扣庫存    │            │  Redis Lua 扣庫存   │
    │  直接回訂單        │            │  202 + 輪詢         │
    │                    │            │                    │
    │  最佳化目標：       │            │  最佳化目標：       │
    │  正確性與彈性       │            │  極致削峰           │
    └────────────────────┘            └────────────────────┘
```

兩條通道**共用領域模型與下游流程**，只在「庫存扣減機制」與「訂單建立路徑」分岔。

> 這條主張要寫成 **ADR-0006**。

### 主張 2：訂單聚合根的多品項重構必須早做

現在的 `SeckillOrder`：

```java
private final Long activityId;   // 單一活動
private final int quantity;      // 單一數量
private final BigDecimal amount; // 單一金額
```

這是**單品項**模型。購物車結帳（一次買 3 件不同商品）根本寫不進去。

必須重構成 `Order` + `OrderLine`：

```
Order (聚合根)
 ├── orderNo, userId, status, addressSnapshot, totalAmount
 └── List<OrderLine>
      └── skuId, skuSnapshot, unitPrice, quantity, subtotal
```

秒殺訂單則是「**只有一條 line 的 Order**」——特例，不是另一種型別。

**為什麼必須早做**：訂單是整個系統的樞紐，付款、履約、退款、對帳全都掛在它上面。
每晚一個階段重構，要一起改的下游就多一層。
這件事的成本會隨時間**指數上升**，拖到 P3 才做等於推倒重來。

> 這條主張要寫成 **ADR-0007**。

### 主張 3：庫存有兩種模型，由統一入口路由

| 商品類型 | 扣減機制 | 理由 |
|---|---|---|
| 一般商品 | MySQL 行 + 樂觀鎖 `UPDATE ... WHERE stock >= ?` | 衝突率低，DB 完全夠用，且天然有交易保證 |
| 秒殺商品 | Redis Lua（現有） | 所有請求競爭同一行，DB 鎖會塌陷 |

這正好呼應 [ADR-0002](../adr/0002-stock-in-redis-not-database.md) 已經寫下的
「重新評估的時機」：

> 若商品從「單一熱點」變成「數萬個低頻 SKU」，衝突不再集中，
> 資料庫樂觀鎖會是更簡單且足夠的方案。

**不是推翻舊決策，是舊決策預見到的分岔點到了。**

應用層只認得一個 `InventoryService`，依商品類型路由到對應實作——
呼叫端不需要知道背後是 Redis 還是 MySQL。

> 這條主張要寫成 **ADR-0008**。

### 主張 4：先切界限脈絡，模組拆分往後延

12 個界限脈絡（詳見 [bounded-contexts.md](bounded-contexts.md)），
但**不要一開始就切成 12 個 Maven 模組**——那會製造大量跨模組樣板，
而多數脈絡根本不需要獨立的生命週期。

演進策略：

```
現在        依「層」分模組，層內單一脈絡
  ↓
第一步      層內改為依「脈絡」分套件，ArchUnit 守跨脈絡邊界
  ↓
需要時      某脈絡證明需要獨立生命週期，才抽成獨立模組
  ↓
真的需要    才考慮拆成獨立服務（多半不會到這一步）
```

**判斷「該抽出去了」的訊號**：這個脈絡的變更頻率、擴縮需求、
或發布節奏明顯偏離其他脈絡。在那之前，套件邊界 + ArchUnit 已經足夠。

### 主張 5：前端是削峰漏斗的第 0 層

秒殺的四層漏斗目前從「本機售罄標記」開始。加上前端後應該是**五層**：

```
第 0 層  前端      按鈕禁用、本地節流、開賣時間校正、CDN 靜態頁
第 1 層  本機標記   Caffeine，奈秒級
第 2 層  多級快取   Caffeine → Redis
第 3 層  Redis Lua  唯一強一致點
第 4 層  Kafka      移出建單
```

**商品頁必須靜態化並由 CDN 完全承接**。100 萬次瀏覽若每次都打到 origin，
還沒到搶購按鈕就先被壓垮了。庫存數字則走獨立的輕量端點，與頁面本體解耦。

詳見 [frontend.md](frontend.md)。

## 三、階段路線圖

每個階段都是**垂直切片**（後端 + 前端），結束時都有能完整 demo 的東西。
不採「先做完所有後端再做前端」——那會讓 API 設計失去真實使用者的驗證。

---

### P0 — 讓現有秒殺真的能用（2–3 週）

現在的秒殺流程走到 `PENDING_PAYMENT` 就斷了。這個階段把它接通。

| 項目 | 標記 | 說明 |
|---|---|---|
| ~~Refresh token + 登出~~ ✅ | `[必要]` | 已完成：15 分鐘 access + 7 天 refresh，含輪替與重用偵測 |
| ~~使用者實體 + 註冊登入~~ ✅ | `[必要]` | 已完成：Identity 脈絡，`dev-token` 後門已移除 |
| 付款（沙盒或模擬） | `[必要]` | `PENDING_PAYMENT → PAID` 目前無人觸發 |
| 秒殺前端頁 | `[必要]` | 商品頁 + 搶購 + 訂單輪詢 |

**完成標準**：能從註冊 → 登入 → 搶購 → 付款 → 看到訂單，全程走完一次。

**注意**：付款不要一開始就串真實金流。先做一個 `PaymentGateway` 埠 +
模擬實作，把訂單狀態機與 Saga 補償跑通；真實串接留到 P3。
先接金流會讓你困在對方的沙盒環境問題裡，而那與架構無關。

---

### P1 — 商品目錄與一般下單（4–6 週）⭐ 最關鍵的階段

| 項目 | 標記 | 說明 |
|---|---|---|
| **Order 聚合根多品項重構** | `[必要]` | 主張 2——這階段不做，後面全部要重來 |
| Catalog 脈絡 | `[必要]` | 商品、SKU、類目、屬性 |
| Inventory 脈絡（雙模型） | `[必要]` | 主張 3，秒殺庫存改由此路由 |
| 一般下單流程（同步） | `[必要]` | 主張 1 的另一條通道 |
| 前端：商品列表 + 詳情 + 直接購買 | `[必要]` | |

**完成標準**：能瀏覽商品、直接下單購買一般商品；秒殺流程不受影響仍正常。

**風險最高的階段**。訂單重構會動到現有的 Outbox 事件、對帳邏輯、
以及 `RedisStockRepository` 的憑證格式。建議做法：

1. 先寫新的 `Order` + `OrderLine` 模型與測試
2. 讓 `SeckillOrder` 成為「單行 Order」的建構捷徑，不刪舊測試
3. 逐步把消費端、對帳、Outbox 遷移過去
4. 全綠後才刪除舊模型

**不要一次性替換**。這個聚合根有 70 支測試在保護它，善用它們。

---

### P2 — 購物車與結帳（3–4 週）

| 項目 | 標記 | 說明 |
|---|---|---|
| Cart 脈絡 | `[必要]` | 未登入用本地，登入後合併 |
| 收貨地址 | `[必要]` | 下單時**快照**進訂單，不可只存 ID |
| 結帳流程 | `[必要]` | 多品項、地址、金額試算 |
| 前端：購物車 + 結帳頁 | `[必要]` | |

**完成標準**：完整的購物體驗——加購物車、改數量、選地址、結帳。

**一個容易錯的細節**：訂單裡的地址、商品名、價格都必須是**快照**。
使用者改了地址或商家調了價，歷史訂單不能跟著變——那是財務問題，不是顯示問題。

---

### P3 — 履約與售後（4–5 週）

| 項目 | 標記 | 說明 |
|---|---|---|
| 付款真實串接 | `[必要]` | 綠界／Stripe 沙盒 |
| Fulfillment 脈絡 | `[必要]` | 出貨、物流狀態 |
| 退款退貨 | `[必要]` | `OrderStatus` 擴充 + 退款 Saga |
| Notification 脈絡 | `[展示]` | 站內信、Email，走既有 Outbox |

**完成標準**：訂單全生命週期閉環——下單、付款、出貨、收貨、退款。

**退款是第二個 Saga**，且比下單補償更複雜：要退錢、退庫存、
處理部分退款、還要防止重複退款。這是展示分散式一致性能力的好題目，
可考慮寫成 **ADR-0011**。

---

### P4 — 營運與成長（持續）

| 項目 | 標記 | 說明 |
|---|---|---|
| 搜尋（ES + CQRS 讀模型） | `[展示]` ⭐ | 技術含量最高的一項 |
| 營運後台 | `[必要]` | 商品上架、活動配置、訂單處理 |
| Promotion 脈絡 | `[展示]` | 優惠券、滿減、價格計算引擎 |
| Review 脈絡 | `[必要]` | 評價 |

**搜尋是這個階段的重點**。用 Outbox 事件同步到 Elasticsearch，
是「事件驅動 + CQRS 讀模型」的教科書級應用，而且**你已經有 Outbox 了**——
邊際成本低、展示價值高。

價格計算引擎（多重優惠疊加、互斥規則）也是很好的領域建模題目。

---

### P5 — 規模化（按需，多半不需要）

| 項目 | 說明 |
|---|---|
| 讀寫分離 | 主從複製 + 讀路由 |
| 分庫分表 | 訂單按 userId 分片 |
| 服務拆分 | 僅當某脈絡真的證明需要獨立生命週期 |

**這個階段預設不做。** 沒有真實流量壓力就做分庫分表，
只會得到一個複雜且無法驗證的系統——那是反效果，不是加分。

若要展示這方面能力，**寫一份「規模化路徑」的 ADR** 說明
「什麼指標達到什麼閾值時該做什麼」，比實際做了更能展現判斷力。

## 五、風險與反模式

### 🔴 會毀掉架構的

**把一般下單塞進秒殺通道。** 主張 1 的反面。症狀是開始出現
「為什麼買一本書也要輪詢」、「這個 SKU 忘了預熱所以買不了」。
一旦走上這條路，兩種場景的最佳化目標會互相拉扯，最後兩邊都做不好。

**訂單重構拖到 P2 之後。** 成本隨掛在訂單上的下游數量指數上升。
P1 做要改 3 個地方，P3 做要改 15 個。

**過早拆微服務。** 現在拆＝把方法呼叫換成網路呼叫，
換來分散式交易、服務發現、鏈路追蹤的全套成本，而收益是零。
[ADR-0001](../adr/0001-modular-monolith-hexagonal.md) 已經有結論。

**God Order 聚合根。** 把秒殺、一般、預購、團購全部塞進同一個聚合根，
用一堆 `if (type == ...)` 分支。正確做法是共用 `Order` 的**結構**，
差異放在建立路徑與策略物件。

### 🟠 會慢慢腐蝕的

**前端直接打領域 API。** 商品頁需要商品 + 庫存 + 評價 + 促銷，
若前端自己發 4 個請求聚合，後端任何重構都會打破前端。
應該有 BFF 層或聚合端點。

**前後端契約漂移。** 建議從 OpenAPI 自動產生 TypeScript 型別
（`openapi-typescript`），讓後端改欄位時前端**編譯就失敗**，
而不是上線後才在瀏覽器 console 發現。

**Outbox 表隨訂單量膨脹。** 已有清理排程，但隨脈絡增加、事件種類變多，
要重新評估保留天數與索引。

**所有商品都預熱進 Redis。** 主張 3 的反面。只有秒殺商品該預熱。

### 🟡 要留意的

- **快照 vs 引用**：訂單裡的價格、商品名、地址必須快照
- **時區**：現在全部用 UTC `Instant`，前端顯示時才轉——別在後端做時區轉換
- **金額精度**：一律 `BigDecimal`，永遠不要用 `double`
- **測試會變慢**：脈絡變多後 Testcontainers 的啟動成本會累積，
  及早規劃共用容器（`@Testcontainers` 的 singleton 模式）

## 六、建議的下一步

不要一次規劃到底。實際的下一步只有三件：
