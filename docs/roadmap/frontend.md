## 一、技術選型

| 項目 | 選擇 | 理由 |
|------|------|------|
| 框架 | **Vue 3 + Nuxt 3** | 原 README 已宣告 Vue；Nuxt 提供逐頁的渲染策略選擇 |
| 語言 | TypeScript | 型別由 OpenAPI 產生，後端改欄位時前端編譯就失敗 |
| 狀態 | Pinia | 購物車、使用者狀態 |
| 樣式 | Tailwind CSS | |
| 測試 | Vitest + Playwright | 單元 + 端到端 |

**選 Nuxt 而非純 Vue SPA，理由只有一個：秒殺場景需要靜態化。**
純 SPA 的首屏要等 JS 下載執行完才有內容，而秒殺開賣前那一分鐘
會有大量使用者同時刷新頁面——那正是最不能慢的時刻。

> 換成 React + Next.js 完全等價，本文的渲染策略與快取設計不變。
> 這個選擇要寫成 **ADR-0009**，重點記錄「為什麼需要 SSG/ISR」而非框架偏好。

## 二、渲染策略（最關鍵的一節）

**不同頁面該用不同策略。** 一律 SSR 或一律 SPA 都是錯的。

| 頁面 | 策略 | 快取 | 理由 |
|------|------|------|------|
| 首頁 | ISR（60s） | CDN | 內容變動慢，流量大 |
| 商品列表 | ISR（60s） | CDN | 同上 |
| 商品詳情 | ISR（300s） | CDN | **SEO 關鍵**，且流量最大 |
| **秒殺活動頁** | **SSG + CDN** | CDN 長快取 | 見下節，最重要 |
| 購物車 | CSR | 不快取 | 純個人資料 |
| 結帳 | SSR | 不快取 | 需要伺服器端價格計算，且不可快取 |
| 訂單列表／詳情 | SSR | 不快取 | 個人資料，需登入 |
| 營運後台 | CSR | 不快取 | 內部工具，SEO 無意義 |

### 秒殺頁的特殊處理

這是前端最需要設計的一頁。**它同時是削峰漏斗的第 0 層。**

```
┌─────────────────────────────────────────────────────────┐
│  靜態部分（SSG，CDN 長快取）                              │
│  商品圖、標題、描述、規格、活動時間                        │
│  → 100 萬次瀏覽，origin 收到 0 次請求                     │
├─────────────────────────────────────────────────────────┤
│  動態部分（客戶端獨立請求）                                │
│  庫存餘量 → GET /api/v1/activities/{id}/stock            │
│  → 極輕量端點，只回一個數字，可高頻                        │
├─────────────────────────────────────────────────────────┤
│  互動部分（開賣後才啟用）                                  │
│  搶購按鈕 → POST /api/v1/seckill/orders                  │
│  → 前端節流：按下後立即 disable，避免重複送出              │
└─────────────────────────────────────────────────────────┘
```

**四個必須做對的細節：**

**① 開賣時間以伺服器時間為準**

客戶端時鐘可能偏差數分鐘。若用 `Date.now()` 判斷開賣，
時鐘快的使用者會提早狂打 API，慢的則錯過開賣。

```
進頁面時取一次伺服器時間 → 計算與本地時鐘的偏移量 → 倒數用「本地時間 + 偏移」
```

**② 開賣瞬間加隨機抖動**

若所有人的倒數同時歸零同時送出請求，會製造一個尖銳到不必要的脈衝。

```
倒數結束後，延遲 random(0, 300ms) 再啟用按鈕
```

**③ 庫存輪詢要退避**

售罄後不該繼續每秒輪詢。

```
有庫存：每 2 秒
售罄：停止輪詢，只在使用者手動重整時再查
```

**④ 訂單輪詢要有上限**

拿到 202 與訂單號後開始輪詢，但**不能無限輪詢**：

```
前 10 秒：每 1 秒
10–30 秒：每 3 秒
超過 30 秒：停止，顯示「處理中，請稍後至訂單頁查看」
```

後端的 `SeckillRequestTracker` 已經支援 `PROCESSING` 狀態，
前端要正確區分「處理中」與「不存在」——後者才是真的失敗。

## 三、認證流程

現在的 JWT 是 **2 小時、無 refresh**。前端無法接受——
使用者填到一半購物車突然被登出。

### 需要補的

```
POST /api/v1/auth/login      → access token (15m) + refresh token (7d)
POST /api/v1/auth/refresh    → 換新的 access token
POST /api/v1/auth/logout     → 撤銷 refresh token
```

### 令牌存放

| 令牌 | 存放位置 | 理由 |
|------|----------|------|
| Access token | **記憶體**（Pinia，不落地） | XSS 也偷不走已關閉的分頁 |
| Refresh token | **httpOnly + Secure + SameSite cookie** | JS 讀不到，XSS 偷不走 |

**不要把 access token 放 localStorage。** 那是 XSS 的直接目標，
任何一個被注入的第三方腳本都能讀走它。

### 自動續期

在 HTTP 攔截器統一處理：

```
請求收到 401
  → 呼叫 /auth/refresh
  → 成功：用新 token 重送原請求
  → 失敗：清除狀態，導向登入
```

**併發要注意**：多個請求同時 401 時，只該發一次 refresh，
其餘請求排隊等結果。否則會用同一個 refresh token 發多次請求，
若後端有 refresh token 輪替機制，後面幾個會全部失敗。

> 這條和後端 Redis 冪等是同一類問題——**併發下的重複請求要收斂成一次**。

## 四、API 契約管理

**這是前後端分離最容易腐爛的地方。**

後端改了欄位名稱，前端毫無感覺地繼續用舊名，
編譯通過、測試通過，上線後才在瀏覽器 console 看到 `undefined`。

### 解法：從 OpenAPI 產生 TypeScript 型別

```
後端 springdoc → /v3/api-docs (OpenAPI JSON)
       ↓
openapi-typescript
       ↓
前端 types/api.d.ts（自動產生，不手改）
```

CI 加一步：**產生型別後若有 diff 就讓建置失敗**，
強迫改動被明確 review 而非悄悄溜過。

後端已經有 springdoc，這一步的邊際成本很低。

### BFF 或聚合端點

商品詳情頁需要：商品資訊 + 庫存 + 評價摘要 + 促銷資訊。

```
❌ 前端發 4 個請求自己聚合
   → 4 次往返、瀑布式載入、後端任何重構都打破前端

✅ 一個聚合端點 GET /api/v1/products/{id}/detail
   → 1 次往返，後端可自由重構內部結構
```

Nuxt 的 server routes 可以直接當 BFF 用，不必額外開服務。

### 建議的建置順序

1. **秒殺頁**（P0）—— 最能驗證現有 API，也最能暴露設計問題
2. 商品列表 + 詳情（P1）
3. 購物車 + 結帳（P2）
4. 訂單中心（P2）
5. 營運後台（P4，可用現成的 admin 模板）

**從秒殺頁開始是刻意的**：它是整個系統最特殊的流程（202 + 輪詢、
倒數、庫存即時性），把它做通，其餘頁面都是相對單純的 CRUD。

## 六、部署

```
使用者 → CDN（Cloudflare／CloudFront）
           ├── 靜態資源（JS/CSS/圖片）      長快取
           ├── ISR 頁面（商品、秒殺）        短快取 + stale-while-revalidate
           └── /api/*  → 回源 Spring Boot   不快取
```

**`stale-while-revalidate` 值得特別用**：快取過期時先回舊內容、
背景更新。使用者永遠不會等待回源，而商品資訊晚幾秒更新完全無害。

秒殺開賣前的流量尖峰幾乎全部由 CDN 承接，origin 只需處理搶購請求本身。

## 七、前端的效能預算

秒殺頁必須訂效能預算，否則它就只是個口號：

| 指標 | 目標 | 為什麼 |
|------|------|--------|
| LCP | < 1.5s | 開賣前使用者會反覆重整 |
| 首屏 JS | < 150KB (gzip) | 行動網路下載時間 |
| 庫存 API 回應 | < 50ms | 已是既有熱路徑的目標 |
| 按鈕可互動 | 開賣前 100% 就緒 | 開賣瞬間才 hydrate 就來不及了 |

最後一項最容易被忽略：**互動能力必須在開賣前就緒**。
若按鈕要等 hydration 完成才能點，開賣瞬間的第一波使用者會全部點空。
