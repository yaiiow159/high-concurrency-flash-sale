# 距離一個完整電商平台，還缺什麼

- 日期：2026-09-04
- 前置：[演進規劃 P0–P5](README.md)（P0–P4 已完成）
- 相關：[界限脈絡](bounded-contexts.md)、[ADR 索引](../adr/README.md)

---

## 一句話結論

**這個系統的架構是完整的，但它還不能真的做生意。**

缺的不是「再多幾個功能」，而是三件讓它從展示品變成商店的東西：
**收得到錢、開得出發票、算得出運費**。這三件缺一，
它就只能是一個跑得很漂亮的原型。

而在那之後，缺的才是使用者會不會留下來的問題。

---

## 這份文件怎麼用

清單本身沒有價值——任何人都能列出「電商還需要推薦系統」。
有價值的是**判準**，因此每一項都要能回答三個問題：

| 問題 | 為什麼重要 |
|---|---|
| **不做會怎樣？** | 分不出「不能營運」與「體驗差一點」，就會先做簡單的那個 |
| **它會改變什麼既有決策？** | 有些功能是加一張表，有些會讓既有的 ADR 失效 |
| **它有沒有一個非做不可的技術問題？** | 沒有的話，它是產品工作而不是架構工作 |

**排序原則：法遵 > 阻斷營運 > 使用者流失 > 展示價值。**
這個順序與「哪個比較有趣」經常是反的，而那正是它值得寫下來的理由。

## 二、現況：架構完整，商業未通

### 已經有的（P0–P4）

十四個界限脈絡、16 份 ADR、427 個 Java 檔。骨幹是完整的：

```
Identity → Catalog → Cart → Ordering → Payment → Fulfillment → Aftersales
                ↘ Seckill ↗            ↘ Promotion  ↘ Review  ↘ Membership
                                        Search（CQRS 讀模型）
                                        Notification（Outbox 驅動）
```

四種「有限資源的併發消耗」都用同一個手法解決（條件式 UPDATE / Lua）：
庫存扣減、優惠券核銷、評分聚合、積分兌換。
三種對帳（庫存、搜尋索引、積分、評分）各自有明確的「修或不修」立場。

### 但它還不能收錢

| 缺口 | 現況 | 後果 |
|---|---|---|
| **真實金流** | 模擬閘道，簽章驗證與冪等都對，但沒接任何一家 | 收不到錢 |
| **電子發票** | 完全沒有 | **台灣法定義務**，開不出發票就不能營業 |
| **運費** | `DiscountType.SHIPPING` 存在但是 no-op，訂單沒有運費欄位 | 每一單都在賠運費 |
| **超商取貨** | 沒有 | 台灣線上零售最大宗的取貨方式 |

**這四項不是「功能」，是營業執照。** 它們的共同點是：
沒有它們，這個系統連一筆真實交易都完成不了。

## 三、缺口分級

### 🔴 P6 — 讓它能真的做生意

#### 1. 真實金流串接

使用者先前明確說過這一項不做，因此**這裡只寫它真正的技術問題**，
留待決定要做的時候用。

現有的 `Payment` 狀態機**假設付款是同步的**：發起 → 導向 → 幾秒內回調。
真實的台灣金流裡，有一半的方式不是這樣：

| 方式 | 生命週期 | 對狀態機的衝擊 |
|---|---|---|
| 信用卡 | 秒級，同步回調 | 現有模型適用 |
| ATM 虛擬帳號 | **取號後三天內付款，也可能永遠不付** | 「待付款」要有 TTL，且必須與訂單逾時關單對齊 |
| 超商代碼 | 同上，且有繳費上限（單筆 2 萬） | 高額訂單要擋在選擇支付方式的那一步 |
| 電子錢包 | 秒級，但回調格式各家不同 | 需要一層轉接 |

**真正的技術問題不是「接 API」，是「取號成功但付款未完成」這個狀態。**
現在的 `PENDING_PAYMENT` 只有一個逾時；ATM 需要的是
「已取號、等待入帳、逾期作廢、且逾期時間由金流商決定」。

還有**對帳檔**：金流商每日提供交易明細，必須與 `payment` 表比對。
這是第五種對帳，而且是唯一一種與外部系統比對的——
前四種都在自己家裡。

> 需要 **ADR-0017：真實金流的多形態付款生命週期**

#### 2. 電子發票

台灣的法定義務，而且它有一個**與這個專案主題完美契合的技術問題**：

**發票號碼是政府配號的有限資源。** 財政部按期別配發字軌
（例如 `AB12345678` 到 `AB12345900`），用完就開不出發票，
而開不出發票就不能出貨。

這正是「有限資源的併發消耗」——與庫存扣減、優惠券核銷、積分兌換
是同一類問題，可以用同一個手法（條件式 UPDATE 取號）。
**做完它，這個專案就有五處用同一個模式解決同一類問題**，
而那比多一個功能有價值得多。

其餘要處理的：

- **載具**（手機條碼／自然人憑證／會員載具）與**捐贈**是三條互斥的路徑
- **折讓單而不是作廢**：退款要開折讓，不是把原發票作廢——
  作廢有時間限制（當期），而退貨常常跨月
- 開立時機：付款成功，不是下單。這與積分入帳在「訂單完成」不同，
  因為稅務認的是收款

> 需要 **ADR-0018：電子發票與號碼配號的併發控制**

#### 3. 運費 ✅ 已完成

見 [ADR-0019](../adr/0019-shipping-fee-model.md)。以下是當初的分析，留作對照。

`DiscountType.SHIPPING` 已經在計價順序的最後一位，ADR-0013 也寫了
「免運門檻看的是折後金額」——**順序想過了，實作是空的**。

要做的：

- 訂單需要 `shippingFee` 欄位，而它會打破一條既有的恆等式：
  現在 `totalAmount == 各行實付加總`，加了運費之後不成立
- 費率維度：**材積或重量取大者**（物流業慣例）、分區（本島／離島）、
  取貨方式（超商 vs 宅配費率不同）
- 免運門檻是一種 `Promotion`，走既有的計價引擎
- **退貨時運費由誰負擔，取決於 `ReturnReason`**——
  `ReturnReason.isSellerFault()` 已經存在且註解就寫著這件事，
  但目前沒有任何地方用它算錢

> 需要 **ADR-0019：運費模型與它對訂單金額恆等式的衝擊**

#### 4. 超商取貨

台灣線上零售最大宗的取貨方式，而它帶來一個**新的訂單終態**：

**「逾期未取」不是退貨，也不是取消。** 貨已經寄出、客人沒去領、
貨退回倉庫。它不是退貨（客人從未收到貨，沒有「驗收」這一步），
也不是取消（已經出貨了，運費已經發生）。

它需要：

- 新的 `Shipment` 狀態（到店 → 逾期 → 退回中 → 已退回）
- 新的訂單終態，以及對應的**庫存回補路徑**
- 退款政策：運費不退（已經發生），商品金額退
- 門市選擇要串第三方 API（電子地圖），而那是一個彈窗回傳的流程

> 需要 **ADR-0020：超商取貨與「逾期未取」終態**

---

### 🟠 P7 — 使用者會離開的

#### 5. 商品圖片與媒體

**目前完全沒有。** 前端用 `ProductTile` 的確定性色塊代替，
那個折衷在展示時說得過去，但沒有人會在看不到商品的情況下買東西。

技術上要決定的：物件儲存（S3 相容）、上傳流程（預簽名 URL 直傳，
不要讓圖片流過應用伺服器）、縮圖規格、CDN。

**這一項的成本被低估了**：它不只是加一個欄位，
而是引入第一個「二進位資產」——備份、遷移、刪除的語意都與資料庫不同。

#### 6. 收藏與到貨通知

缺貨是常態，而現在缺貨的使用者**直接流失**，沒有任何承接。
到貨通知走既有的 `Notification` 脈絡，成本低、價值高。

#### 7. 搜尋進階

已經有 CQRS 讀模型、CJK 分析器、品牌分面。還缺：

- **依評分排序**——ADR-0014 明確 scope out 過，理由是要改
  `ProductSearchIndex` 的埠。那個理由仍然成立，但這是還債的時候
- 價格區間分面、多選篩選
- 自動完成與搜尋詞建議（需要 completion suggester）
- 同義詞（「筆電」vs「筆記型電腦」）

#### 8. 商品問答

比評價更早影響決策——評價是買完之後，問答是買之前。
資料模型比評價簡單（沒有評分聚合），但多一個「商家回覆」，
而那需要商家身分（見 P9）。

---

### 🟡 P8 — 展示價值高、且與本專案主題契合

#### 9. 防黃牛與風控 ⭐

**這是目前最大的主題性缺口。**

這個專案的一句話理解是「讓注定失敗的 99.9% 請求以最低成本被擋下」。
但那句話只處理了**流量**，沒處理**意圖**——
黃牛不是注定失敗的請求，他是**不該成功卻會成功**的請求。

一個秒殺系統沒有防黃牛，就像一個金庫沒有鎖：
所有的併發正確性都做對了，然後 90% 的貨被腳本買走。

要做的：

- **裝置指紋與行為評分**：下單前的頁面停留時間、滑鼠軌跡、
  請求間隔的規律性。腳本的特徵是「太快、太準、太規律」
- **多帳號關聯**：同一裝置／同一收貨地址／同一支付工具的多個帳號
- **風險分數進入熱路徑**——而這是難點：
  熱路徑目前只有 Redis 與 Kafka 各一次，多一次風控查詢會破壞那個上限。
  可行解是把分數**預先算好放進 Redis**，讓熱路徑只多讀一個 key
  （或直接併進 `seckill_deduct.lua`，變成零額外往返）
- 灰度處置：不要直接拒絕（會讓黃牛知道被偵測到），
  而是降級——排到隊尾、加驗證碼、或靜默失敗

> 需要 **ADR-0021：風控分數如何在不增加熱路徑往返的前提下生效**

#### 10. 分散式追蹤

已經有 Prometheus + Grafana + 告警規則，但**沒有 tracing**。

真正的問題不是「接個 OpenTelemetry」，而是
**trace context 要跨越 Outbox 與 Kafka**：
一筆秒殺請求的 trace 在寫進 outbox 那一刻就斷了，
而下游的訂單建立、通知、積分入帳全部變成孤兒 span。

要做的是把 traceparent 存進 `outbox_event` 的一個欄位，
中繼器投遞時放進 Kafka header，消費端還原。
**那才是這一項的技術內容**，而它正好展示了對非同步系統可觀測性的理解。

#### 11. 個資合規（刪除帳號）

「刪除我的帳號」與「訂單必須保留七年」直接衝突。

正解是**匿名化而非刪除**：把 `app_user` 的識別欄位洗掉，
訂單保留但指向一個匿名主體。而這裡有一個這個專案特有的難題——

**`Order` 上的 `ShippingInfo` 是快照，而它含姓名、電話、地址。**
那份快照就是個資，匿名化必須動到它；
但它被 `updatable = false` 鎖住，理由是「出貨紀錄不可竄改」（ADR-0011）。

兩條規則直接對撞，而解法必須是一個明確的決定
（例如：只有匿名化流程能改，且改的動作本身要留稽核紀錄）。

> 需要 **ADR-0022：帳號匿名化與不可變快照的衝突**

### ⚪ 明確不做（以及理由）

| 項目 | 為什麼不做 |
|---|---|
| **多賣家 marketplace** | 它**改變一切**：商品歸屬、庫存歸屬、分帳、退款由誰出錢、運費由誰算、客服找誰。不是加一個 `sellerId` 欄位，而是重新定義每一個聚合根的擁有者。要做就是一次獨立的大重構，不該夾在功能清單裡 |
| **推薦系統** | 需要行為資料（瀏覽、加購、購買序列），而現在一筆都沒有。先做**行為事件收集**才有意義；沒有資料的推薦系統只是一個協同過濾的範例程式碼 |
| **分庫分表 / 讀寫分離** | P5 已經說明：沒有真實流量壓力就做，只會得到一個複雜且無法驗證的系統。寫一份「什麼指標到什麼閾值才做」的 ADR 比實作更有價值 |
| **多語系 / 多幣別** | 沒有跨境需求時，它是純粹的成本。而且它會滲透進每一個 DTO |
| **積分過期** | ADR-0016 已列。它會把消費順序變成先進先出問題，流水結構要跟著改 |
| **會員專屬價** | 會打破「價格一律由目錄決定」這條很乾淨的規則。值得多留一陣子 |

## 三之二、壓測之後才看得到的缺口（2026-09-05 補）

上面那份清單是**讀程式碼**列出來的。這一節是**跑起來量**之後才浮現的，
形態不同：它們在小資料量下完全不存在，要有 5 萬件商品與
每秒上千請求才會現形。

### 1. 削峰有深度，但沒有上限、沒有監控、也沒有告訴使用者 🔴

實測（[ADR-0020](../adr/0020-order-create-partition-key.md)）：

| | 數值 |
|---|---|
| 入口（Redis 扣減）吞吐 | 1,448 QPS |
| 出口（建單）吞吐 | 182 TPS |
| 落差 | **8 倍** |

削峰本來就預期入口快於出口，佇列存在的意義就是吸收尖峰。
**但這個系統對「佇列有多深」一無所知。**

- **沒有任何 consumer lag 指標**。`alert-rules.yml` 有 9 條告警，
  涵蓋庫存漂移、對帳、熔斷、延遲——**沒有一條看佇列積壓**。
  `OutboxEventsStuck` 量的是建單「速率」，不是「還欠多少」，
  而積壓時速率是正常的
- 壓測時 78,037 則訊息積在佇列裡超過半小時，**不會觸發任何告警**
- 使用者拿到訂單號之後輪詢，而系統**說不出「大概多久」**。
  庫存扣掉了、訂單還不存在，這段期間的長度目前沒有人知道

三件該做的事，由淺到深：

1. **把 lag 變成一級指標**（Kafka exporter 或消費端自行上報），
   並加一條告警。這是純工，但沒有它，上面兩項都無從談起
2. **給使用者一個誠實的預估**：訂單頁的「處理中」應該說得出
   「前面還有 N 筆」。資料就在 lag 裡
3. **入場控制**：lag 超過閾值時**停止接受新請求**，回「活動太熱門」。
   這是一個真正需要判斷的決定——它等於主動放棄一部分成交，
   換取「已經接下的請求會在合理時間內完成」這個承諾。
   不做的話，尖峰時系統會接下遠超它能消化的量，
   而那些人全部要等，且沒有人告訴他們要等多久

> 需要 **ADR-0023：佇列深度作為服務水準，以及入場控制的取捨**

**這一項與這個專案的主題是同一件事。** 「讓注定失敗的請求以最低成本被擋下」
講的是拒絕；這裡講的是**接下來之後的承諾**，而目前那個承諾是空的。

### 2. 排序完全沒有 🟠

`/catalog/products` 與 `/search/products` 都**沒有 sort 參數**，
前端也沒有排序 UI。列表永遠是 `id DESC`（近似「最新」）。

依價格、銷量、評分排序是電商的基本盤，而它現在一個都沒有。

技術上它不是加一個參數就好——[ADR-0021](../adr/0021-keyset-pagination.md)
的「不做的事」已經寫下這個相依：

> 游標與排序鍵綁死。若之後要支援「依價格排序」，keyset 的游標必須是
> `(價格, id)` 複合值——單一欄位不足以定位，因為價格會重複。

也就是說，**排序功能的技術內容是複合游標的編碼**，不是 ORDER BY。
這件事必須在加排序時一起想，不能事後補。

### 3. 沒有「銷量」這個概念 🟠

資料庫裡**沒有任何已售出的聚合**（確認過所有 migration）。
因此做不到：熱賣排序、「已售 1,234 件」的社會證明、暢銷榜。

它與 `product_rating` 是同一型的問題——衍生聚合，走增量 UPDATE
（CLAUDE.md 7-3 那條規則），而且同樣**存總數不存比率**。
成本低，而且它是上面「依銷量排序」的前提。

要決定的只有一件事：**在哪個時點加**。付款成功還是訂單完成？
退貨要不要扣回？（積分那條規則說要扣，這裡應該一致）

### 4. 庫存在列表與商品頁完全看不到 🟠

商品詳情頁**完全沒有請求庫存**。使用者看不到「剩 3 件」，
也看不到「已售完」——缺貨商品照常出現在列表裡，
點進去、加入購物車、到結帳才失敗。

庫存不進商品頁的快取是對的（ADR 已經記過：變動頻率不同的資料
不該共用快取），**但「不快取」不等於「不顯示」**——
它應該像評分那樣在客戶端另外取。

這一項也是「收藏與到貨通知」（P7-6）的前提：
沒有缺貨狀態，就沒有地方掛「到貨通知我」。

### 5. 後台商品清單沒有分頁 🟡

storefront 的分頁已經修好（ADR-0021），**後台還是老樣子**：
載入一次 20 筆，沒有下一頁、沒有跳頁、也沒有搜尋。
5 萬件商品的後台，實際上只看得到最新的 20 件。

後台維持 offset 分頁是 ADR-0021 決策 4 的結論（維運要能跳頁），
但那份 ADR 說的是**後端不動**，前端該有的分頁 UI 仍然缺席。

### 6. 「我的訂單」沒有任何篩選 🟡

沒有狀態篩選、沒有日期區間、沒有搜尋。訂單一多就只能一直往下捲。

## 四、階段計畫

### 依賴關係

```
P6（能做生意）
  金流 ──┬─→ 發票（開立時機綁付款成功）
         └─→ 對帳檔
  運費 ──┬─→ 超商取貨（費率不同）
         └─→ 訂單金額恆等式要改

P7（留住使用者）
  商品圖片（獨立，可平行）
  收藏／到貨通知（獨立，可平行）
  搜尋進階 ──→ 依評分排序（需改 ProductSearchIndex 埠）
  商品問答 ──→ 商家回覆（需要 P9 的商家身分，可先做不含回覆的版本）

P8（規模與信任）
  防黃牛 ──→ 需要熱路徑的預算討論（ADR-0021）
  分散式追蹤（獨立，但要動 outbox schema）
  個資合規 ──→ 與 ADR-0011 的不可變快照衝突

P9（平台化，想清楚再做）
  多賣家 ──→ 會讓上面每一項都要重看一遍
```

### 排程

| 階段 | 內容 | 預估 | 完成後的狀態 |
|---|---|---|---|
| **P6** | ~~運費~~ ✅、發票、超商取貨、金流（使用者已延後） | 6–8 週 | **可以真的營業** |
| **P7** | 圖片、收藏、搜尋進階、問答 | 4–6 週 | 使用者願意留下來 |
| **P8** | 防黃牛、追蹤、個資合規 | 4–5 週 | 撐得住惡意流量與稽核 |
| **P9** | 多賣家 | 未估 | 從商店變成平台 |

**如果只能做一件事：P6 的發票。**
它是法遵硬需求，而且它的技術核心（配號的併發消耗）
與這個專案已經解決過四次的問題同型——投入產出比最高。

**如果目標是作品集展示：P8 的防黃牛。**
它補上了這個專案主題上唯一的洞，
而且「風控如何在不增加熱路徑往返的前提下生效」是一個
真正需要判斷力的問題，不是體力活。

## 六、建議的下一步

0. **（新）先把 consumer lag 變成看得見的東西**。它是純工、半天的量，
   但沒有它，「系統現在健不健康」這個問題目前答不出來——
   壓測時 7.8 萬則訊息積了半小時，九條告警一條都沒響
1. **先決定商業意圖**：這是作品集，還是要真的上線？
   - 作品集 → 直接跳 P8 的防黃牛，它的展示價值最高
   - 要上線 → P6 沒有捷徑，而且發票要先申請字軌
2. **P6 的四項裡，運費最先做**：超商取貨依賴它，
   而且它會改動訂單的金額恆等式——越晚改，要動的地方越多
3. **不要先做多賣家**。它會讓上面每一項都要重新想一遍
