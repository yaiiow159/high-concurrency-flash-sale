# ADR-0013：優惠計算引擎與折扣的快照邊界

- 狀態：已接受
- 日期：2026-09-04
- 相關：[ADR-0007](0007-multi-line-order-aggregate.md)（多品項訂單）、
  [ADR-0006](0006-dual-order-channels.md)（雙通道）、
  [ADR-0002](0002-stock-in-redis-not-database.md)（庫存不在資料庫）

---

## 背景

目前訂單金額就是各行小計的加總。加入優惠之後，
「這張訂單為什麼是這個金額」會變成一個需要好幾個步驟才能回答的問題——
而那個問題正是客服每天要回答的。

優惠是這個系統第一個**同時牽動金額、庫存與併發**的功能：

- 金額：折扣算錯就是財務問題
- 庫存：滿額贈品要扣庫存，而那是另一條扣減路徑
- 併發：一張券只能用一次，而「檢查有沒有用過」到「標記已使用」中間有窗口

---

## 決策

### 1. 計算引擎是純函式，放在領域層

引擎的輸入是「訂單行 + 可用的優惠規則」，輸出是「折扣明細」。
**不查資料庫、不呼叫任何遠端服務、不看時鐘**（時間由呼叫端傳入）。

這讓「三件商品套用滿千折百再套八折券的結果是多少」變成一個
可以用單元測試窮舉的問題，不需要啟動任何東西。
優惠的規則會越長越複雜，而複雜的規則只有在能被便宜地驗證時才安全。

### 2. 計算順序寫死，而且順序本身是業務決定

多重優惠疊加時，**順序決定最終金額**。先打八折再減 100，
與先減 100 再打八折，差距是 20 元。

固定順序：

```
1. 單品折扣（特價、單品限量折扣）  → 改變每一行的實付單價
2. 訂單折扣（滿減、整單折扣）      → 對折後小計計算
3. 優惠券                          → 對前兩步之後的金額計算
4. 運費                            → 最後計算，因為免運門檻看的是折後金額
```

**券排在滿減之後**，是因為滿減是商家的活動而券是給特定人的補償或行銷；
讓券先算會讓「滿千折百」的門檻更難達到，等於用券懲罰使用者。
這是可以有不同答案的商業決策，但它必須是<b>一個</b>答案且寫下來——
散在各處的隱含順序是優惠系統最典型的腐爛方式。

### 3. 折扣必須進訂單快照，而且是「明細」不是「總額」

訂單只存一個 `discountAmount` 是不夠的。客服要回答的是
「為什麼折了 320」，而那需要知道是哪幾個優惠、各折了多少。

因此訂單存一份 `OrderDiscount` 清單（來源、名稱、金額），
與 `OrderLine` 的快照同一個道理：**優惠會下架、券會過期、規則會改**，
而三個月後的客訴要看的是當時的規則。

存 `promotionId` 引用是錯的——那是 ADR-0007 已經解決過的同一個問題。

### 4. 秒殺不與任何優惠疊加

秒殺價本身就是優惠。疊加會造成三個問題：

- **價格不可預測**：秒殺價已經逼近成本，再打折可能變成負毛利
- **庫存經濟性失效**：秒殺的庫存量是按秒殺價算出來的
- **通道差異滲透**：要支援疊加，領域層就得知道「這一行是不是秒殺」，
  而那正是 ADR-0006 明文禁止的（`channel` 只用於追溯，不可用於控制流程）

判斷依據不是 `order.channel()` 而是 **`line.sourceActivityId() != null`**——
那是「這一行的價格從哪裡來」，是更精確的事實。
與關單退庫用同一個判準，理由也相同。

### 5. 分攤的餘數給金額最大的那一行

整單折扣要分攤回每一行（退款要按行退，行的實付價必須加總等於訂單總額）。
而百分比分攤幾乎必然除不盡：三行各 333.33 元的訂單打九折，
每行 300.00 加起來是 900.00，但總額應該是 899.99 或 900.01。

規則：**逐行無條件捨去到分，餘數加到金額最大的那一行**。

- 捨去而非四捨五入：對商家有利的方向捨去會讓實收大於折後應收，
  那是收多了；反過來則是給錯折扣。兩者都不對，但「少折給使用者」
  會被客訴，「多折」則會被財務發現——選一個會被發現的
- 餘數給最大行：給最小行時，餘數相對於該行的比例最大，
  退那一行時的誤差最明顯

**這條規則的價值在於它被寫下來且被測試釘住**，而不在於它是唯一正確的。
沒有明文規則時，每個經手的人都會用自己的直覺，
而那些直覺加總起來就是對不平的帳。

### 6. 券的使用必須是單一原子語句

「查券沒用過 → 建立訂單 → 標記券已使用」是 read-modify-write，
兩個併發請求會讓同一張券用兩次。

這與退貨額度那次是同一類問題，但解法不同：退貨用悲觀鎖鎖訂單列，
券則用**條件式 UPDATE**：

```sql
UPDATE coupon SET status = 'USED', order_no = ?, used_at = ?
WHERE id = ? AND status = 'ISSUED'
```

受影響列數為 0 就代表已被使用，拒絕。檢查與寫入在同一個語句內，
中間插不進東西——與 `InventoryJpaRepository.deductAvailable` 同一個手法。

**不要用分散式鎖**：臨界區完全可以原子化，加鎖只是多一個會失敗的東西。

### 7. 券在下單交易內核銷，失敗一起回滾

券的核銷與訂單建立必須同生共死。分開做的話：

- 先核銷後建單：建單失敗則券白白消失
- 先建單後核銷：核銷失敗則訂單享受了折扣但券還在

兩者都在同一個資料庫交易裡，天然原子——這是「不要跨資源」原則的又一次應用。

### 8. 折後金額必須分攤回每一行並存下來

實作時發現一個原本不在計畫內、但**會安靜流錢**的缺口：
退款是按行退的，而退款金額原本用 `unitPrice × quantity` 算。

整單折扣折在**訂單**上，退貨卻是退**一行**。
有折扣的訂單，那個乘積是使用者沒有付過的錢。

更麻煩的是既有的防線攔不住它：

- 全額退貨會超過已付金額，被 `Payment` 的退款上限擋下
- **部分退貨不會**——一筆 40000 的訂單折了 2000、實付 38000，
  退掉其中一行定價 20000 的商品，退出去 20000 而使用者為那一行只付了 19000。
  20000 遠低於 38000 的上限，那道防線完全不會作聲

因此 `order_line` 多一個 `allocated_amount`：整單折扣分攤下來的實付金額。
它是**快照**，與 `unit_price` 同一個道理——分攤是下單當時算的，
規則之後怎麼改都不該影響已成立的訂單。

分次退貨用**累計分攤**而非逐次計算：

```
本次退款 = ⌊實付 × (已退 + 本次) / 總數⌋ − ⌊實付 × 已退 / 總數⌋
```

一行 3 件實付 100.00，逐次捨去是 33.33 × 3 = 99.99，每行漏掉幾分錢；
用累計差額則餘數自然落在最後一次，全部退完剛好是 100.00。
不需要另外記「已經退了多少錢」——退貨件數本來就查得到。

`Order.place` 在建立當下驗證兩條恆等式（各行實付加總 == 折後應付，
且 小計 − 折扣加總 == 折後應付）。這是最便宜的攔截點：
分攤算錯不會拋例外、不會被上限擋下，只會讓退款按一組數字算、
收款按另一組，半年後對帳才發現。

---

## 不做的事

- **滿額贈品**。它要扣庫存，而那是第二條扣減路徑，
  會把「優惠」與「庫存」兩個脈絡黏在一起。值得單獨做一次
- **會員等級價**。需要會員體系的等級模型，目前沒有
- **優惠的 A/B 測試與個人化發券**。需要行為資料
- **運費計算**。目前模型裡沒有運費，第 4 步在實作上是 no-op，
  但順序先定下來，之後補運費時不必再爭一次

---

## 後果

**好的：**

- 計算引擎是純函式，複雜規則的組合可以窮舉測試
- 折扣明細進快照，客訴時拿得出當時的計算過程
- 券的併發安全靠單一 SQL 語句，沒有引入新的協調機制

**要付出的：**

- 訂單多兩張表（折扣明細、券）與兩個欄位
  （`order_line.allocated_amount`、`return_line.refund_amount`），
  對帳要多考慮兩條恆等式：
  <b>訂單總額 == 行小計加總 − 折扣加總</b>，以及
  <b>訂單總額 == 各行實付加總</b>
- `return_line.refund_amount` 不再能由單價推導，必須存下來。
  少了它，退貨單就不是自我完備的稽核憑證
- 計算順序寫死意味著改順序是一次破壞性變更——
  已成立的訂單用舊順序算，新訂單用新順序，兩者無法互相驗算。
  這也是折扣明細必須存下來的另一個理由
