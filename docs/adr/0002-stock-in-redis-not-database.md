# ADR-0002：庫存餘量放 Redis，不放聚合根與資料庫

**狀態**：已採納
**日期**：2026-08-28

## 脈絡

DDD 的標準教法是「不變條件應由聚合根守護」。庫存不能為負，是典型的不變條件，
按教科書就該放進 `SeckillActivity` 聚合根，由資料庫交易保證一致。

但秒殺場景的流量特徵讓這個做法直接失效：**所有請求都競爭同一行資料**。
1000 件庫存可能湧入 100 萬次請求，全部指向同一個 `activity_id`。

## 選項

**A. 資料庫悲觀鎖**（`SELECT ... FOR UPDATE`）

所有請求在同一行上排隊。MySQL 單行鎖的極限約每秒數百到數千次，
且鎖等待會迅速耗盡連線池，連不相關的查詢也一併卡死。

**B. 資料庫樂觀鎖**（`UPDATE ... WHERE stock >= ? AND version = ?`）

不會鎖等待，但高衝突下失敗率極高——1000 個並發只有 1 個成功，其餘 999 個重試。
重試又製造新的衝突，形成活鎖。這個方案在低衝突場景很好，在秒殺場景是最糟的選擇。

**C. Redis 原子扣減 + 資料庫最終對帳**（本方案）

熱點資料移到單執行緒的記憶體資料庫，扣減成為 O(1) 且天然序列化。

## 決策

**庫存餘量由 Redis 承擔，資料庫只保留活動配置與訂單紀錄。**

聚合根 `SeckillActivity` 的 `totalStock` 僅為配置的初始總量，
**不參與扣減判斷**，只用於預熱與對帳。

一致性由三層保證：

1. **Redis Lua**：扣減的原子性（防超賣）
2. **`request_id` 唯一索引**：訂單不重複（防重複下單）
3. **Saga 補償**：訂單關閉時退回庫存（防少賣）

## 代價

- **放棄了強一致，接受最終一致。** Redis 扣減成功到訂單落庫之間有一段窗口，此期間庫存已被佔用但訂單尚不存在。這正是 `SeckillRequestTracker` 存在的原因——讓前端在這段窗口內看到 `PROCESSING` 而非 404。
- **Redis 成為單點。** 因此 `RedisStockRepository` 在 Redis 故障時**拒絕降級放行**：寧可整個活動不可用，也不能無上限超賣。這與限流器的 fail-open 策略刻意相反，取捨依據是「失效的後果」。
- **需要對帳機制。** Redis 餘量與訂單數的一致性沒有資料庫交易保證，偏差不會自癒，只會累積。已實作 `StockReconciliationService`：每 10 分鐘核對 `Redis 餘量 + Σ(未取消訂單數量) = 活動總庫存`，並掃描孤兒扣減（庫存已扣、訂單不存在）。自動修復預設關閉——有 bug 的自動修復，破壞力大於它要修的問題。
- **重新評估的時機**：若商品從「單一熱點」變成「數萬個低頻 SKU」，衝突不再集中，資料庫樂觀鎖會是更簡單且足夠的方案，此時應撤掉 Redis 這一層。
