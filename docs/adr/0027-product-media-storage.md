# ADR-0027：商品圖片與第一個二進位資產

- 狀態：已接受
- 日期：2026-09-06
- 相關：[ADR-0002](0002-stock-in-redis-not-database.md)（庫存放 Redis）、
  [ADR-0012](0012-search-read-model.md)（搜尋讀模型）、
  [ADR-0015](0015-operations-console.md)（營運後台）

---

## 背景

商品目錄沒有圖片欄位。前台用 `ProductTile` 從 ID 推導一個確定性色塊代替，
那個折衷在展示時說得過去，但**沒有人會在看不到商品的情況下買東西**。

這是這個系統第一次要存<b>不是資料的東西</b>。而真正的成本不在
「加一個 URL 欄位」，在於二進位資產的**備份、遷移、刪除語意
全部與資料庫不同**——那三件事目前都由 MySQL 的交易與備份一手包辦，
加了物件儲存之後就不是了。

---

## 決策

### 1. 物件儲存，不進資料庫

圖片不存 BLOB。理由不是「檔案很大」，而是三個具體的後果：

- **備份會膨脹到無法操作**。目前整個 flash_sale 資料庫幾百 MB，
  五萬件商品各三張圖就是數十 GB——而備份與還原的時間直接決定
  事故的復原時間
- **複製會被拖垮**。BLOB 走 binlog，主從延遲會從毫秒變成秒級，
  而那條複製鏈上還有對帳與報表
- **資料庫變成 CDN 的源站**。每一次圖片請求都佔一條連線，
  而連線池是秒殺熱路徑要跟它搶的東西

用 S3 相容介面（MinIO 本機開發、正式環境換 endpoint 即可），
不綁特定雲廠商。

### 2. 預簽名直傳，位元組不經過應用伺服器

**這是這份 ADR 最重要的一條，而理由是這個專案特有的。**

一張 5 MB 的圖片若走應用伺服器轉發，那條請求執行緒會被佔住數秒。
而秒殺熱路徑要的正是那個執行緒池——營運在後台上傳商品圖，
會直接吃掉當下能承接搶購的併發數。這與
[ADR-0015](0015-operations-console.md) 的立場一致：
**後台的成本不該由正在下單的使用者承擔。**

流程：

1. 後台請求上傳授權，應用伺服器回一個**預簽名 PUT URL**——
   這一步是純 CPU（簽章），零 I/O
2. 瀏覽器直接 PUT 到物件儲存
3. 上傳完成後回報，應用伺服器才寫資料庫

伺服器全程沒有碰到那幾 MB。

### 3. 內容雜湊當檔名，不是流水號

物件鍵是 `{sha256}.{ext}`，不是 `product-123-1.jpg`。

- **同一張圖上傳兩次只有一個物件**。商家換規格重傳、多個商品共用
  同一張情境圖都很常見
- **URL 不可變，所以 CDN 可以永久快取**。用可變的鍵
  （`product-123.jpg`）的話，每次換圖都要清 CDN 快取，
  而那是一個會忘記做、且忘記了不會有錯誤訊息的步驟——
  症狀是「我明明換了圖，客人還是看到舊的」

這也讓商品頁的 ISR 快取（[ADR-0021](0021-keyset-pagination.md) 那一輪加的）
可以放心快取圖片 URL：URL 不會變，變的是商品指向哪一個 URL。

### 4. 尺寸在上傳時預先產生，不做即時縮放

上傳完成後產生固定幾組（縮圖 / 列表 / 詳情），一次做完。

即時縮放（`?w=400`）看起來更彈性，實際上是把每一次圖片請求
變成一次 CPU 工作，而且快取鍵會隨著參數組合爆炸——
一張圖在 CDN 上可能有幾十份。

**縮圖在慢車道做**：上傳回報後投遞一則訊息，由消費端產生。
原圖先可用，縮圖晚幾秒到——那幾秒商品還沒上架，沒有人看得到。

變體的鍵由原圖推導（`{sha256}_{thumb|list|detail}.{ext}`），不另外存。
推導是純函式，因此消費端重放整個 topic 只是把同樣的位元組寫到同樣的鍵——
CLAUDE.md 鐵則 4 的第二題「把歷史全部重跑一次會怎樣」在這裡的答案是沒事。

**有些圖永遠不會有變體，而那是正確的終局，不是待修的狀態。**
JDK 的 ImageIO 解不開 WebP；原圖比目標還小時放大只會得到模糊又更大的檔案。
兩種情況都不產、不標記 `variants_ready`，前端沿用原圖。
換句話說 `variants_ready = 0` 有兩種意思——「還沒輪到」與「不會有了」——
而**呼叫端不需要分辨**，兩者的正確行為都是用原圖。
硬要分辨就得再存一個狀態欄，而那個欄位除了讓人看報表以外沒有用途。

**部分產生不可標記。** 三個尺寸只成功兩個就標記的話，
前端會去要那個不存在的尺寸，而那是破圖——比沒有縮圖糟得多。

**由後端挑用哪一個網址，不讓前端拼變體名稱。**
API 一次回 `url` / `listUrl` / `thumbUrl` 三個完整網址，
前端照用途取用。命名規則洩漏到前端之後就再也改不動了，
而「變體還沒好時退回原圖」這個邏輯若複製到前端，
每個呼叫端都要記得寫，漏一個就是破圖。

### 5. 刪除是最難的一件事，而且沒有乾淨解

資料庫的刪除可以在交易裡；物件儲存**不能參與那個交易**。
因此兩種失敗一定會發生其中一種：

| 順序 | 失敗時的結果 |
|---|---|
| 先刪物件、再刪資料庫列 | 商品指向一個不存在的圖 → **破圖** |
| 先刪資料庫列、再刪物件 | 沒有人指向的物件留在桶裡 → **孤兒** |

選後者。孤兒只花錢，破圖直接砸在客人臉上。

因此：**商品下架或刪除時完全不動物件**。清理由一個獨立的
對帳排程負責，而它必須：

- 有**明顯長於**任何進行中的上傳流程的寬限期——
  剛上傳、還沒掛到商品上的物件看起來就是孤兒
- 與庫存對帳同一個立場（[CLAUDE.md 規則 8](../../CLAUDE.md)）：
  **預設只報告，不自動刪除**。「這個物件沒有人指向」這個判斷
  一旦有 bug，代價是永久性的資料遺失，而那沒有補償路徑

這是系統的**第六條對帳**，也是第一條與外部儲存比對的。

### 6. 上傳先於掛載，順序不可反過來

物件先進儲存，成功之後才寫資料庫的關聯。

反過來（先寫資料庫、再上傳）的失敗模式是商品指向一個不存在的物件，
而那與第 5 點是同一個判斷：**寧可有孤兒，不可有破圖**。
這也與庫存劃撥的順序規則同型（先動 MySQL 再寫 Redis，
反過來會讓同一批貨被賣兩次）。

### 7. 備份與還原：兩個系統要一起想

先前「還原資料庫」是一個完整的動作。加了物件儲存之後不是了。

| 情況 | 結果 |
|---|---|
| 資料庫還原到昨天 + 桶是今天的 | 桶裡有沒人指向的物件 → **孤兒，可接受** |
| 資料庫是今天 + 桶還原到昨天 | 商品指向今天上傳的物件 → **破圖** |

因此還原順序是：**先還原物件儲存到不早於資料庫的時間點**。
寫進 runbook，不要等到事故當下才推導。

物件儲存本身開版本控制，讓誤刪有救。

## 不做的事

- **圖片審核（違規、侵權）**。需要人工流程或外部服務，
  而它是一個營運決策不是技術決策
- **浮水印、AI 去背、自動裁切**。這些都是「處理」而不是「儲存」，
  應該在縮圖那條慢車道上加，屬於另一份 ADR
- **使用者上傳（評價曬圖）**。它多了一整套風險：未經審核的內容
  會出現在商品頁上。先做商家圖片，那條路徑的來源是可信的
- **多張圖的排序介面**。純 CRUD，沒有技術決策
- **圖片的 CDN 設定**。它是部署配置而不是程式碼；
  內容雜湊命名已經把「可以永久快取」這個前提準備好了

---

## 後果

**好的：**

- 商品終於看得見。這是目前前台最大的視覺缺口
- 上傳不佔用秒殺要用的執行緒
- 內容雜湊讓 CDN 與 ISR 都能放心永久快取

**要付出的：**

- **多一個必須備份、必須監控、必須一起還原的系統**。
  這是最大的一筆，而且它不會出現在功能清單上
- **孤兒物件會累積**，且清理預設不自動執行——
  這是刻意的，代價是要有人定期看那份報告
- **本機開發多一個容器**（MinIO）。`docker compose` 又長一點，
  而新人的第一次啟動又慢一點
- **圖片上傳失敗的處理散在前端**。位元組不經過伺服器的代價是
  伺服器也不知道上傳有沒有成功——只能靠前端回報，
  而回報本身可能丟失。這正是第 5 點那個寬限期存在的原因
