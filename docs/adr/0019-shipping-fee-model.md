# ADR-0019：運費模型與它對訂單金額恆等式的衝擊

- 狀態：已接受
- 日期：2026-09-04
- 相關：[ADR-0013](0013-promotion-pricing-engine.md)（優惠計算引擎）、
  [ADR-0011](0011-refund-saga.md)（退款）、
  [ADR-0007](0007-multi-line-order-aggregate.md)（多品項訂單）

---

## 背景

`DiscountType.SHIPPING` 從 ADR-0013 起就存在，而且排在計算順序的最後一位，
理由當時就寫清楚了：「免運門檻看的是折後金額」。

**但它是空的。** 訂單沒有運費欄位、沒有費率、沒有計算。
每一單的運費都由商家自行吸收——那不是一個可以營業的狀態。

真正需要決定的不是「運費怎麼算」（那是查表），而是
**運費放進去之後，既有的金額恆等式怎麼辦**。

---

## 決策

### 1. 運費是訂單層級的金額，不分攤到訂單行

ADR-0013 決策 8 建立了一條恆等式：

```
Order.totalAmount == Σ OrderLine.allocatedAmount
```

它讓退款可以按行退，而且加總一分不差。**運費不能進去。**

分攤運費到行看起來對稱，實際上會製造一個沒有答案的問題：
退一行要退多少運費？三件商品一起寄，退掉其中一件——
配送這件事已經發生了，沒有「三分之一趟」這種東西。

因此運費是**訂單層級**的：

```
Order.totalAmount      == Σ OrderLine.allocatedAmount   ← 不變
Order.payableAmount()  == totalAmount + shippingFee     ← 新的
```

`totalAmount` 的語意保持「商品折後應付」，**它不改名**——
改名要動 API 契約、前端、既有訂單的解讀，而換來的只是一個更精確的詞。
用一個新的 `payableAmount()` 表達「這張訂單總共要付多少」更便宜。

### 2. 付款與退款上限用 `payableAmount`，不是 `totalAmount`

這是這份 ADR 最容易做錯的地方。

`Payment.amount` 目前取自 `totalAmount`。不改的話，運費就收不到——
而且**沒有任何東西會發現**：付款成功、訂單完成、貨也寄了，
只有月底對帳時發現每一單都少收幾十元。

退款上限同理。它現在是 `Payment.amount`，只要付款金額對了，
退款上限就自動跟著對——這是把上限綁在付款而不是訂單上的好處。

### 3. 運費由「材積重量取大者」決定，而不是只看重量

物流業的計價慣例：`max(實際重量, 材積重量)`。
一箱衛生紙很輕但佔滿整個貨車，只按重量算會賠死。

材積重量 = 長 × 寬 × 高 / 材積係數（台灣常見 6000）。

**但目前 SKU 只有重量沒有尺寸。** 這一版先做重量，
把材積留成明確的 TODO——因為加三個尺寸欄位很容易，
而讓商品建立表單多三個必填欄位是一個產品決策。

### 4. 費率放資料庫，不放程式碼

運費是**營運會調的東西**（換物流商、油價、促銷檔期），
而每次調整都要改程式碼並重新部署是不合理的。

費率表的維度：`(配送方式, 區域, 重量上限) → 費用`。
查表時取「重量上限 >= 訂單重量」裡最小的那一筆。

**沒有做後台編輯介面**——那是純 CRUD，沒有技術決策，
而且改費率是一件應該慢、應該有人覆核的事。目前用遷移種資料。

### 5. 區域由郵遞區號推導，不由使用者選

離島運費是本島的兩到三倍，而讓使用者自己選區域等於讓他選價格。

`ShippingInfo` 已經有 `postalCode`，推導是純函式。
台灣的離島郵遞區號是固定的幾段（澎湖 880–885、金門 890–896、
馬祖 209–212、綠島 951、蘭嶼 952），寫死在領域層。

**推導不到就當本島。** 這個方向是對商家不利的（少收運費），
而反過來（當成離島多收）會讓使用者在結帳頁看到一個他無法理解的金額。

### 6. 免運是 `Promotion`，走既有的計價引擎

不另外做一個「免運門檻」欄位。免運就是一個 `DiscountType.SHIPPING`
的優惠，而它排在最後正是因為門檻要看折後金額（ADR-0013 決策 2）。

這讓「滿 1000 免運」與「滿 1000 折 100」用同一套規則、同一個後台、
同一份快照進訂單。多做一個平行的機制只會讓兩者慢慢長出不同的行為。

**折抵上限是運費本身**：免運券折不出比運費更多的錢。

### 7. 退貨時運費退不退，由 `ReturnReason` 決定

`ReturnReason.isSellerFault()` 早就存在，而且它的註解就寫著
「決定運費由誰負擔」——但**沒有任何地方用它算錢**。

規則：

| 情況 | 運費 |
|---|---|
| 賣方責任（瑕疵、不符、出錯貨）且**全額退貨** | 退 |
| 買方改變心意 | 不退（配送已經發生，成本是真的） |
| 部分退貨 | 不退（貨還是寄了那一趟） |

「全額退貨」的判準是**這次退完之後訂單沒有任何可退的東西了**，
而不是「這張退貨單涵蓋所有品項」——分兩次退完應該與一次退完結果相同。

---

## 不做的事

- **材積重量**。需要 SKU 多三個尺寸欄位，而那是產品決策（建立商品的表單會變長）。
  留成 TODO，`ShippingFeeCalculator` 的簽章已經預留
- **超商取貨**。它是下一份 ADR（0020），因為它帶來一個新的訂單終態
  （逾期未取），而那比費率複雜得多。這一版只有宅配
- **多件合併運費 / 分箱**。真實物流會依材積拆箱，各箱各算。
  那需要裝箱演算法，而目前沒有材積
- **運費的後台編輯介面**。純 CRUD，沒有技術決策；
  而且改費率是一件應該慢、應該有人覆核的事
- **貨到付款的手續費**。它與運費不同——那是金流成本，
  屬於 ADR-0017 的範圍

---

## 後果

**好的：**

- 原有的恆等式 `totalAmount == Σ allocatedAmount` **完全不動**，
  退款按行退的邏輯一行都不必改
- 免運與其他優惠共用同一套規則、同一份快照
- 運費退不退有一個明確且可測的判準，而不是客服each case 判斷

**要付出的：**

- **多一條恆等式要維護**：`Payment.amount == Order.payableAmount()`。
  它沒有自動檢查——付款是在下單之後才發起的，
  而那時訂單已經存起來了。**這是這份 ADR 引入的最大風險**：
  如果哪天有人改了運費的計算而忘了付款那一側，
  症狀是「收的錢與訂單顯示的不一樣」，而且只有對帳會發現
- SKU 多一個重量欄位，而**既有商品的重量是 0**。
  遷移時給一個預設值（1000 克），否則所有既有商品都會變成免運
- 訂單的金額顯示從一個數字變成三個（商品、運費、總計），
  前端每一處顯示金額的地方都要看一遍
