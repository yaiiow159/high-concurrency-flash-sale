# ADR-0014：評價的可信度與評分聚合

- 狀態：已接受
- 日期：2026-09-04
- 相關：[ADR-0007](0007-multi-line-order-aggregate.md)（多品項訂單）、
  [ADR-0012](0012-search-read-model.md)（搜尋讀模型）、
  [ADR-0002](0002-stock-in-redis-not-database.md)（讀寫比決定資料放哪）

---

## 背景

評價功能表面上是一張 CRUD 表，實際上有兩個真正的問題：

1. **可信度**——評價一旦可以任意張貼，它就一文不值。
   而「一文不值」不是慢慢發生的，是從第一則刷出來的評價開始的
2. **讀寫比**——商品頁每次載入都要顯示平均分與評價數，
   而評價本身很少被寫入。這是這個系統裡讀寫比最懸殊的資料之一

第二點在庫存那裡已經回答過一次（[ADR-0002](0002-stock-in-redis-not-database.md)）：
**讀寫比決定資料放哪、以什麼形狀放**。這裡的答案不同，但問法一樣。

---

## 決策

### 1. 評價必須綁定一筆「已完成」的訂單行

評價的主鍵語意是 `(orderNo, skuId)`，不是 `(userId, skuId)`。

三道條件缺一不可：

- 訂單屬於這個使用者
- 訂單狀態是 `COMPLETED`（已送達）——付了錢但還沒收到貨的人，
  對商品本身還沒有意見
- 這筆訂單行還沒被評價過（唯一索引擋住）

**綁訂單行而不是綁使用者**，是因為同一個人可以買同一件商品兩次，
而那是兩次獨立的購買經驗，本來就該能各評一次。
反過來說，綁使用者會讓「買兩次只能評一次」，那是憑空的限制。

**這道檢查不能只做在應用層。** 唯一索引 `uk_review_order_sku (order_no, sku_id)`
是最後一道——兩個並行請求會同時通過「還沒評價過」的查詢。
與訂單的 `request_id` 唯一索引同一個角色。

### 2. 聚合存 (sum, count) 而不是 average

商品頁要顯示「4.3 分，128 則評價」。三種做法：

| 做法 | 問題 |
|---|---|
| 每次查詢 `AVG(rating)` | 商品頁每次載入都掃一次該商品的所有評價 |
| 聚合表存 `average` | **算不出來**——新增一則評價要重算平均，而重算需要 count |
| 聚合表存 `rating_sum` + `rating_count` | 可增量更新，平均由兩者相除 |

存平均值是最直覺、也最錯的選擇：它把「可以增量維護」這個性質丟掉了。
這與庫存流水記 `availableDelta` 與 `allocatedDelta` **兩個增減量**
而不是單一 quantity 是同一件事（見 CLAUDE.md 3-1）——
**存導出值就重建不出原始事實**。

順帶還存五個分佈欄位（`count_1` … `count_5`），
因為電商的評價區一定要有那條長條圖，而它同樣不該靠掃全表算出來。

### 3. 聚合的更新是條件式增量 UPDATE，不是讀出來算再寫回

```sql
UPDATE product_rating
   SET rating_sum = rating_sum + :delta,
       rating_count = rating_count + :countDelta,
       count_4 = count_4 + :bucket4, ...
 WHERE product_id = :productId
```

**不要 SELECT 出來在 Java 裡加完再 UPDATE**——那是 read-modify-write，
兩個人同時評價同一件商品時會有一則被吃掉。

這與 `InventoryJpaRepository.deductAvailable` 與券的核銷是同一個手法，
而它們在這個專案裡已經出現第三次了：**能壓成一句 SQL 的，就不要用鎖。**

差別在於這裡的 UPDATE **沒有守衛條件**——評分沒有「不足」這種狀態，
任何 delta 都是合法的。因此受影響列數為 0 只代表「這個商品還沒有聚合列」，
要補一筆再重試，不是錯誤。

### 4. 修改評價用 delta，因此必須留著舊評分

給七天的修改窗口。使用者收到貨當下的情緒與一週後的使用感受本來就不同，
不給改只會逼他們刪掉重寫——而刪掉重寫要處理的併發問題更多。

修改時聚合的更新是：

```
rating_sum += (new - old)
rating_count += 0
count_{old} -= 1, count_{new} += 1
```

`rating_count` 不變是這裡唯一容易寫錯的地方。
而 `old` 從資料庫**當場讀出來的那一列**取，不是從請求帶進來——
呼叫端若能宣告舊評分是多少，它就能把平均分改成任何值。

### 5. 評分不進 `product` 表

Catalog **不認得** Review。`product_rating` 是獨立的一張表，
商品頁的評分由應用層組裝兩個來源。

理由與 `Address`/`ShippingInfo`、`promotion`/`order` 一樣：
一旦 `Product` 上有 `averageRating` 欄位，Catalog 就得知道評價什麼時候會變、
誰負責維護它，兩個脈絡從此黏死。

**代價是商品列表要多一次查詢**（批次取多個商品的評分），
那是可以接受的——它是一次以主鍵為條件的批次查詢，不是 N+1。

### 6. 顯示名稱在寫入時就遮蔽，不是在畫面上遮

評價列表顯示「王＊＊」而不是完整姓名。

遮蔽**在建立評價時就寫進 `author_name` 快照**，理由有兩個：

- 前端遮蔽等於完整姓名仍然出現在 API 回應裡，開一下開發者工具就看得到
- 使用者日後改暱稱，三個月前的評價不該跟著變——
  那是別人看過並據以決定要不要買的內容（同 `OrderLine` 的快照）

### 7. 評分不進搜尋索引（本次不做）

原本打算讓 ES 的商品文件帶上評分，好支援「依評價排序」，
走的是與商品變更同一條 Outbox 路徑（[ADR-0012](0012-search-read-model.md)）。

**實作時決定不做**，因為它不是加一個欄位那麼簡單：
`ProductSearchIndex.index(Product)` 與 `reindexAll()` 都得改成帶著評分，
而後者在基礎設施層自己迭代商品——等於讓搜尋的轉接器認得 Review。
那是一次跨脈絡的改動，值得單獨做一次而不是夾在評價功能裡。

畫面上的星等改由**批次查聚合表**取得（決策 5 的那次批次查詢），
使用者看得到的東西沒有少；少的是「依評分排序」這個搜尋選項。

---

## 不做的事

- **依評分排序搜尋結果**。理由見決策 7——它要改的是搜尋子系統的埠，
  不是評價功能的一部分

- **評價圖片**。需要物件儲存與圖片處理，那是另一條完整的路徑
- **「這則評價有幫助」投票**。它本身又是一套防刷問題（誰能投、能投幾次），
  而且會讓評價的排序變成一個需要調的參數
- **商家回覆**。需要商家身分，目前的角色模型只有 CUSTOMER 與 ADMIN
- **評價審核佇列**。真實電商需要，但它是營運流程不是技術問題，
  做出來只會是一張待審清單
- **依評分篩選評價列表**（只看一星）。加上去很容易，
  但它會讓分頁的游標邏輯多一個維度，而展示價值接近零

---

## 後果

**好的：**

- 評價的可信度有三道實質約束（訂單擁有、訂單已完成、一行只評一次），
  最後一道在資料庫層
- 聚合可增量維護，商品頁不必掃評價表
- 併發安全靠一句 SQL，沒有引入新的協調機制——這是本專案第三次用同一個手法

**要付出的：**

- 聚合表與評價表之間存在「可能不同步」的空間。
  兩者在同一個交易內更新，因此正常路徑不會分岔；
  但若日後有人繞過 `ReviewService` 直接寫 `review` 表，聚合就會失準。
  **需要一支對帳**（`SELECT SUM(rating), COUNT(*) FROM review GROUP BY product_id`
  比對 `product_rating`），與庫存對帳同一個道理
- 商品列表多一次批次查詢
- 七天修改窗口意味著「已經有人看過並據以決定購買的評價會變」。
  這是真實電商的普遍做法，但它確實是一個取捨
