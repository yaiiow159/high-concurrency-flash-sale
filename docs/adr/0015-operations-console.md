# ADR-0015：營運後台的邊界

- 狀態：已接受

---

## 背景

後台的端點大多已經存在——出貨、退貨審核、上下架、對帳、重建索引——
它們是各功能做到一半時順手長出來的，散在六個控制器裡，
只能用 `curl` 呼叫。

「營運後台」這件事真正要決定的不是要不要做，而是**它跟商店的關係**：
同一個應用還是兩個？權限畫在哪裡？後台的查詢會不會拖垮線上流量？

第三個問題是這裡唯一有技術風險的：後台的清單查詢天生是
「掃一大段資料、沒有使用者維度、可以很慢」，而那正是熱路徑最怕的鄰居。

---

## 決策

### 1. 後台與商店同一個前端應用，用 `/admin` 路由前綴

不另外開一個部署。理由是**共用的東西遠多於不共用的**：
設計語彙、API 型別、認證與續期、錯誤處理。拆成兩個 Nuxt 應用意味著
那四樣各維護兩份，而後台的流量是商店的千分之一——
它撐不起「獨立部署」的維運成本。

代價是後台的程式碼會被打進商店的 bundle。用**路由層級的動態載入**
（Nuxt 預設就是 per-route code splitting）之後，
沒進過 `/admin` 的訪客不會下載那些 chunk。

### 2. 前端的路由守衛<b>不是</b>安全邊界

這是整份 ADR 最重要的一條，也是最容易搞錯的一條。

`/admin` 的中介層只做一件事：**沒有 admin scope 的人不要看到後台的殼**。
它防的是「誤觸」與「畫面上出現一堆按下去會失敗的按鈕」，不是防攻擊者。

真正的授權在 `SecurityConfig`：

```java
.requestMatchers("/api/v1/admin/**").hasAuthority(SCOPE_ADMIN)
```

**任何新增的後台功能，安全性一律由後端那條規則保證。**
前端守衛可以被繞過（改 JS、直接打 API），而那不重要——
因為繞過之後打到的每一支 API 都還是會回 403。

推論：後台**不新增任何「只有前端知道」的規則**。
例如「只有 admin 能看到全部訂單」不能靠前端不顯示入口來達成，
必須是後端那支端點本身就要 admin scope。

### 3. 後台頁面完全不做 SSR

`/admin` 底下一律 `ssr: false`。兩個理由：

- **內容全是營運資料與個資**。它們不該出現在任何可能被快取的 HTML 裡，
  而商品頁與首頁正是 ISR 快取的（ADR-0009）——同一個應用裡混著兩種渲染策略時，
  最安全的做法是讓後台明確退出
- 後台沒有 SEO 需求，也沒有首屏速度的壓力。SSR 在這裡只有壞處

### 4. 後台的清單查詢一律分頁，而且上限寫死在後端

沒有「全部載入」這個選項。後台的資料量本來就比前台大一個數量級
（前台看自己的十張訂單，後台看所有人的十萬張），
而後台的使用者只有幾個人——他們按一下「載入全部」的成本，
會由當下所有正在下單的使用者一起承擔。

上限由**後端**夾住而不是前端傳什麼就給什麼。前端傳 `size=100000`
必須被截到上限，而不是被信任。

### 5. 商品建立：SPU 與 SKU 一起建，不允許沒有 SKU 的商品

`Product` 沒有 SKU 就不可販售——它不是「還沒建完的商品」，
而是一個**永遠不會出現在任何地方**的殘骸：列表要顯示最低價，
而最低價來自 SKU。

允許先建商品再補 SKU，等於在資料庫裡製造一批看不見也刪不掉的東西。
因此建立端點要求至少一個 SKU，這是聚合根的完整性，不是表單驗證。

**新建的商品一律是 `DRAFT`**，不直接上架。上架是一個獨立的動作，
因為它會觸發搜尋索引寫入（ADR-0012）——建立與曝光是兩件事，
中間那段時間正是給人檢查有沒有打錯字用的。

### 6. 不可逆與高成本的操作要二次確認

「釋放活動庫存」「重建搜尋索引」「標記送達」屬於這一類：
前兩個成本高且不可逆，第三個會啟動退貨期限的計時。

確認對話框是**前端的責任**，後端不因此多一個 `confirm=true` 參數——
那種參數只會被自動化腳本無腦帶上，防不了任何東西，
卻讓 API 多一個沒有語意的欄位。

---

## 不做的事

- **角色細分**（客服／倉管／財務各有各的權限）。
  目前的角色模型只有 `CUSTOMER` 與 `ADMIN`，細分需要一套權限模型，
  而那是一個獨立的功能而不是後台的一部分
- **操作稽核紀錄**（誰在什麼時候改了什麼）。真實系統必須有，
  但它應該是一個橫切關注點（AOP 或 outbox），不該由後台頁面各自寫
- **批次操作**（一次出貨 50 張）。每一筆的失敗處理都不同，
  批次介面會把「哪幾筆失敗了」變成一個新的 UI 問題
- **後台專用的統計圖表**。營運數字該從 Grafana 看，
  那裡已經有 Prometheus 的資料；在後台重畫一次只是多一份會過時的實作

---

## 後果

**好的：**

- 既有的後台端點終於有了入口，不必再用 `curl`
- 權限邊界只有一處（`SecurityConfig`），前端守衛純粹是 UX
- 後台與商店共用設計語彙，看起來是同一個產品

**要付出的：**

- 後台程式碼在同一個 repo 與同一個應用裡，
  日後若真的需要獨立部署，要先把它拆出來
- `/admin` 的中介層會讓人誤以為那是安全機制。
  這一點只能靠註解與這份 ADR 說清楚——**它擋不住任何人**
- 新增後台功能時要記得同步兩件事：後端的 scope 規則與前端的選單。
  漏了前者是安全問題，漏了後者只是找不到入口
