# ADR-0003：以 Lua 原子性取代分散式鎖

**狀態**：已採納
**日期**：2026-08-28

## 脈絡

「秒殺防超賣」的常見答案是「用 Redisson 分散式鎖」。
這個答案在多數教學文章中出現，但它其實回答錯了問題。

需要分散式鎖的前提是：**存在一段必須互斥、且無法原子化的臨界區**。
典型的錯誤實作長這樣：

```java
Integer stock = redis.get(key);      // 讀
if (stock > 0) {                     // 判斷
    redis.decr(key);                 // 寫
}
```

讀、判斷、寫之間有兩個空隙，並發下必然超賣。
於是有人在外面包一層分散式鎖把整段互斥掉——這確實能修好正確性，
但它修的是「自己製造出來的問題」。

## 選項

**A. Redisson 鎖包住讀-判斷-寫**

正確，但每次請求需要：取鎖（1 RTT）+ 業務操作（2 RTT）+ 解鎖（1 RTT）= 4 次往返，
且所有請求在鎖上完全串行化。並行度被壓成 1。

**B. Lua 腳本**（本方案）

把讀、判斷、寫寫進同一份腳本。Redis 以單執行緒執行整個腳本，
腳本內天然互斥，且只需 **1 次往返**。

## 決策

**庫存扣減與退回一律使用 Lua 腳本，不使用分散式鎖。**

Redisson 仍然保留，但只用在真正需要互斥、且無法原子化的低頻場景：

| 場景 | 為什麼需要鎖 |
|------|--------------|
| 庫存預熱 | 讀 DB → 寫 Redis 跨越兩個系統，無法原子化 |
| 快取重建 | 防止熱點 key 過期瞬間大量請求同時回源（快取擊穿） |
| 排程節點互斥 | 多副本部署時只需一個節點執行 |

這三者的共同點：**低頻**。用鎖串行化的代價可以忽略。

## 代價

- **Lua 腳本的可測試性較差。** 沒有 IDE 除錯器，錯誤到執行期才會浮現。對策是把腳本放在獨立的 `.lua` 檔（可用 `redis-cli --eval` 手動驗證），並以 `RedisStockRepositoryTest` 對真實 Redis 做併發驗證——用 mock 測這段等於什麼都沒測。
- **腳本必須保持簡短。** Redis 執行腳本期間會阻塞所有其他指令，一個慢腳本會拖垮整個實例。本專案的腳本都在 10 條指令以內。
- **叢集模式的限制。** 多鍵腳本要求所有鍵落在同一個 slot，因此 `RedisKeys` 使用 hash tag（`seckill:{a1001}:stock`）強制同槽。忘記這件事的話，腳本在單機測試正常、上叢集立刻報 `CROSSSLOT`。
- **Redisson 不使用官方 starter。** `redisson-spring-boot-starter` 會連帶接管 `RedisConnectionFactory`，把整個 Redis 存取層換成 Redisson 實作。本專案的熱路徑是為 Lettuce 調校的，因此改為手動建立 `RedissonClient`，讓它只承擔鎖這一項職責。
