# ADR-0001：模組化單體 + 六角架構

**狀態**：已採納
**日期**：2026-08-28

## 脈絡

秒殺系統的元件邊界相當清晰：活動、庫存、訂單、補償。
很容易直覺地拆成四個微服務，但這個專案的實際約束是：

- 團隊規模小，沒有專職的平台團隊維運服務網格與分散式追蹤
- 秒殺的熱路徑對延遲極度敏感，每多一次跨服務呼叫就多一次 RTT 與一個故障點
- 真正需要獨立擴縮的只有兩個角色：**接單的 API** 與 **消費建單的 worker**

## 選項

| 方案 | 優點 | 缺點 |
|------|------|------|
| 微服務（4 個） | 獨立部署、技術異質 | 熱路徑多次 RTT；分散式交易複雜度暴增；維運成本遠超團隊能負擔 |
| 傳統分層單體 | 開發最快 | 分層極易腐化；Service 層很快變成上帝物件；業務邏輯與框架糾纏 |
| **模組化單體 + 六角架構** | 邊界清晰且由編譯器強制；日後可依模組邊界拆分 | 仍是單一部署單元；需要額外的紀律維持邊界 |

## 決策

採用**模組化單體 + 六角架構（Ports & Adapters）**，切分為四個 Maven 模組：

```
flash-sale-domain          純 Java，零框架依賴
flash-sale-application     Use Case 編排 + Port 介面
flash-sale-infrastructure  Redis / MySQL / Kafka 的 Adapter 實作
flash-sale-api             HTTP 入站 Adapter + 組裝根
```

依賴方向嚴格由外往內，**並由 `ArchitectureTest`（ArchUnit）在 CI 強制驗證**。
用 Maven 模組而非套件切分，是因為模組邊界由編譯器保證：
應用層根本拿不到 `RedisTemplate` 這個類別，不是「不該用」而是「用不了」。

## 代價

- 單一部署單元。若 API 與 worker 的資源需求差異拉大，需以不同的 profile 啟動同一份成品來區隔角色（目前已可透過關閉 `@Scheduled` 與 Kafka listener 達成）。
- 模組間轉換需要 Mapper（Entity ↔ 聚合根 ↔ DTO），程式碼量比直接共用一個類別多。這是刻意付出的代價：共用模型意味著資料庫結構的變更會直接傳導到 API 契約。
- **重新評估的時機**：當某個模組的變更頻率或擴縮需求明顯偏離其他模組時（例如活動管理後台需要獨立的營運節奏），應優先把該模組拆出去。目前的模組邊界已經是未來的服務邊界。
