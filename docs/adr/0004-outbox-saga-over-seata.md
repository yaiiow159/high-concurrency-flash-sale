# ADR-0004：Outbox + Saga 取代 Seata 分散式交易

**狀態**：已採納
**日期**：2026-08-28

## 脈絡

秒殺流程橫跨三個無法共用交易的資源：

1. **Redis**：庫存扣減
2. **Kafka**：建單訊息投遞
3. **MySQL**：訂單落庫

任何一步成功而後續失敗，都會產生不一致：
庫存扣了但訂單沒建（**少賣**）、訂單建了但庫存沒扣（**超賣**）。

## 選項

**A. Seata AT 模式**

侵入性最低，靠 undo log 自動回滾。但 AT 模式會對每一筆變更加**全域鎖**，
在秒殺這種所有請求競爭同一資源的場景，全域鎖的爭用會比資料庫行鎖更嚴重——
它把瓶頸從資料庫搬到了 TC（Transaction Coordinator），而且 TC 是新的單點。

**B. Seata TCC 模式**

效能較 AT 好，但每個操作要寫 Try/Confirm/Cancel 三份程式碼，
且 Redis 與 Kafka 都需要自行實作 TCC 介面。實作成本與出錯機率都很高。

**C. Outbox + Saga 補償**（本方案）

不追求「同時成功或同時失敗」，改為**先確保不遺失，再以補償修正**。

## 決策

### Outbox：讓事件投遞與業務資料原子一致

訂單落庫與領域事件寫入 `outbox_event` 表，**在同一個資料庫交易中完成**。
兩張表在同一個資料庫裡，因此天然原子——不需要任何協調者。

再由 `OutboxRelayScheduler` 非同步把事件搬到 Kafka。

```
[DB 交易] 訂單 INSERT + outbox INSERT  ──commit──▶  必定都成功或都失敗
                    │
             [中繼器 1s 輪詢]
                    ▼
              Kafka （至少一次）
```

代價是「至少一次」語意，因此**所有消費端都必須冪等**——這不是可選項，是使用 Outbox 的前提。

### Saga：以補償取代回滾

```
扣減庫存 ──▶ 投遞訊息 ──▶ 建立訂單 ──▶ 等待付款
    │            │             │            │
    │            │             │            └─逾時─▶ 關單 ─┐
    │            │             └─重試耗盡─▶ DLQ ──────────┤
    │            └─投遞失敗─▶ 立即退庫                     │
    └───────────────────── 退回庫存 ◀───────────────────────┘
```

三個補償觸發點：

| 觸發點 | 處理者 | 特性 |
|--------|--------|------|
| 訊息投遞失敗 | `SeckillApplicationService` 同步補償 | 最快，使用者當下就知道結果 |
| 建單重試耗盡 | DLQ 消費端 | 訂單不存在，只能依訊息內容退庫 |
| 逾時未付款 | 關單排程 + Outbox 事件 | 量最大，也最容易被忽略 |

**退庫必須冪等**——三個路徑可能對同一筆訂單同時發起補償。
冪等由 Lua 腳本的 `requestId` 映射保證：退庫時刪除映射，重複呼叫因找不到映射而直接返回。

### 為什麼補償不放在關單的交易裡？

因為 Redis 無法加入資料庫交易。若在交易內退庫、交易隨後回滾，
庫存會憑空多出來——**這比少賣更嚴重，是超賣**。

正確順序是「先 commit 關單 + 退庫事件，再由事件驅動退庫」。

## 代價

- **不是強一致。** 從訂單關閉到庫存退回有秒級延遲，此期間商品顯示為售罄但實際有貨。對秒殺場景可接受。
- **所有消費端必須冪等**，這個約束是全域的，任何新增的消費者都要遵守。程式碼上以 `request_id` 唯一索引與 Lua 冪等鍵強制。
- **多了一張表與一個排程。** Outbox 表的寫入量等同訂單量，需要定期清理（已實作 `deletePublishedBefore`），否則幾次大促後 `findPending` 的掃描成本會顯著上升。
- **重新評估的時機**：若團隊已有成熟的 Seata 維運能力，且業務要求「下單即刻強一致」（例如金融場景），TCC 模式會是更合適的選擇。秒殺不屬於這類場景。
