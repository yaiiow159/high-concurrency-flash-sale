# ADR-0020：建單訊息的分區鍵改用訂單號

- 狀態：已接受
- 日期：2026-09-05
- 相關：[ADR-0004](0004-outbox-saga-over-seata.md)（Outbox + Saga）、
  [ADR-0002](0002-stock-in-redis-not-database.md)（庫存放 Redis）

---

## 背景

`seckill.order.create` 的分區鍵原本是 `activityId`，註解寫著

> 同一活動的訊息落在同一分區，方便消費端做批次與有序處理

這句話描述的是一個**沒有被實作出來的設計**。實際的消費端
（`OrderCreationService.createFrom`）是：

- 一次處理**一則**訊息，各自開一個 `@Transactional`
- 冪等靠 `saveIfAbsent` 與 `request_id` 唯一索引
- 每張訂單彼此獨立，不讀取前一則訊息留下的狀態

也就是說，**既沒有批次，也不依賴順序**。分區鍵換來的東西沒有人在用。

而它的代價，剛好打在這個系統存在的理由上。

---

## 問題：秒殺的定義就是流量集中在同一場活動

用 `activityId` 當鍵，一場秒殺的所有訊息會雜湊到**同一個分區**。
Kafka 的分區是消費並行度的單位——一個分區同時只會有一個消費者執行緒。

於是：不論開幾個分區、`concurrency` 設多少，**實際只有一個執行緒在建單**。

壓測實測（50 萬庫存、12 分區、`order-create-concurrency: 6`）：

```
GROUP                 TOPIC                PARTITION  LAG
seckill-order-creator seckill.order.create 6          68201
seckill-order-creator seckill.order.create 0..5,7..11 0
```

78,037 則訊息**全部落在 partition 6**，其餘 11 個分區完全是空的。

| 指標 | 數值 |
|---|---|
| 入口（Redis 扣減）吞吐 | 1,448 QPS |
| 建單（消費端）吞吐 | 38 TPS |
| 差距 | **38 倍** |

削峰本來就預期入口快於出口——佇列存在的意義就是吸收尖峰。
但 38 倍不是削峰，是**堰塞湖**：50 萬份庫存要花超過三小時才變成訂單，
而使用者還在輪詢他的訂單號。

更糟的是它**看起來是設定好的**：12 個分區、6 個消費執行緒，
監控上也看得到 6 個 consumer 已分配到分區。
只有去看每個分區的 lag，才會發現 5 個執行緒整場都是閒著的。

---

## 決策

**分區鍵改用 `orderNo`。**

```java
public String partitionKey() {
    return orderNo;
}
```

理由：

1. **高基數且均勻**。訂單號是雪花 ID，散佈到各分區近乎平均，
   消費並行度回到分區數與 `concurrency` 的較小值
2. **同一張訂單的重投仍落在同一分區**。at-least-once 的重送
   相對它自己仍然有序，這是分區鍵唯一真正需要保證的事
3. **不需要跨訂單的順序**。每張訂單獨立成立，這一點由
   `saveIfAbsent` 與唯一索引保證，與訊息先後無關

---

## 不做的事

- **不改成批次消費**。批次能再提升吞吐，但它會讓「一則訊息一個交易」
  變成「一批共用一個交易」，而那會把單筆失敗的影響面從一張訂單
  放大到整批。要做的話應該是獨立的一份 ADR，並且先把
  部分失敗的處理方式想清楚
- **不調高 `order-create-concurrency`**。瓶頸不是執行緒數，
  是分區分佈；鍵沒改之前，把 6 改成 60 一樣只有一個執行緒在做事
- **不減少分區數**。12 個分區沒有錯，錯的是所有訊息都進同一個

---

## 後果

**好的：**

- 建單吞吐不再被單一活動綁死在一個執行緒上
- 「12 分區 / concurrency 6」這組設定終於名副其實

**要付出的：**

- **失去了「同一活動的訊息相鄰」這個性質**。目前沒有任何邏輯依賴它，
  但將來若真的要做批次建單，會需要重新考慮鍵的設計——
  屆時正確的做法是讓鍵帶上活動與一個分桶（例如 `activityId + userId % N`），
  而不是退回純 `activityId`
- **既有佇列中的訊息鍵不一致**。部署當下佇列裡的舊訊息仍以 activityId 分區，
  它們會照舊被消費完，不需要特別處理——消費端對鍵沒有任何假設

---

## 給後人的提醒

這個 bug 的形態值得記下來：**註解描述的是意圖，不是行為。**

「方便消費端做批次與有序處理」讀起來完全合理，
而且它讓後來的人不會去質疑這個鍵——因為理由已經寫在那裡了。
真正該問的是「**誰在用這個性質**」，而答案是沒有人。

同一次壓測還找到另一個同型的問題：`ProductJpaRepository.findLowestPrices`
早就寫好了批次查詢並註明「避免 N+1」，但從來沒有被接上，
列表頁實際上仍在逐筆 lazy 載入。

**寫下來的意圖不會自己變成程式碼。**
