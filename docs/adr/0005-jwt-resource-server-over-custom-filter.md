# ADR-0005：以 OAuth2 Resource Server 承載認證

**狀態**：已採納
**日期**：2026-08-29
**取代**：先前以 `X-User-Id` 標頭傳遞身分的臨時做法

## 脈絡

專案初期為了聚焦在併發主題，身分以 `X-User-Id` 標頭傳遞。
這個做法的問題不是「不夠完整」，而是**完全沒有認證**：

```bash
curl -H "X-User-Id: 任意數字" ...     # 冒用任何人的身分
```

更嚴重的是它讓限流形同虛設——攻擊者每次換一個號碼就能繞過單一使用者限流，
而那道限流正是擋腳本刷單的主力。

## 選項

**A. Session + Redis 集中儲存**

熟悉、可撤銷。但每個請求都要讀一次 Redis 取 session，
等於在熱路徑上憑空增加一次網路往返——這與整個削峰設計直接衝突。

**B. 自刻 JWT 過濾器**

依賴少、可控。但令牌驗證需要正確處理簽章、`exp`、`nbf`、`iss`、`aud`、
演算法混淆攻擊（`alg: none`、HS256/RS256 互換）等等，
每一項都有對應的 CVE 歷史。**這是典型的「自己實作密碼學相關邏輯」陷阱**。

**C. Spring Security OAuth2 Resource Server**（本方案）

上述驗證項目全部由框架處理，且能無縫接上外部 IdP。

## 決策

採用 **OAuth2 Resource Server + JWT**，本地開發以 HMAC（HS256）對稱金鑰簽章。

- 使用者身分取自標準的 `sub` claim，不用自訂欄位——換 IdP 時不需對方配合
- 權限以 `scope` claim 表達，Spring Security 自動轉為 `SCOPE_` 前綴的權限
- **驗證受眾（`aud`）**：少了這項，同一個 IdP 簽給其他服務的令牌
  也能拿來存取本服務
- 管理端點（庫存預熱）要求 `seckill:admin` scope

### 為什麼 JWT 能待在熱路徑上

因為驗證是**純 CPU 運算**（HMAC 約數十微秒），不需要任何遠端呼叫。
這是它相對於 Session 的決定性優勢，也是唯一的理由。

**推論出的鐵則**：絕不可為了取得使用者資料而在認證環節查資料庫。
需要的資訊必須全部放在 claim 裡；一旦開始回查，這個優勢就消失了。

## 2026-09-01 修訂：令牌雙軌設計

**原決策仍然成立**（OAuth2 Resource Server + JWT），本節修訂的是其中兩條代價。

### 為什麼修訂

原文把「令牌無法即時撤銷」列為無狀態設計的固有代價，並認為唯一的解法是
黑名單、而黑名單會把 Redis 查詢加回熱路徑。

**這個推論有個隱含前提：只有一種令牌。**

一旦允許兩種令牌，撤銷需求可以完全落在低頻的那一種上，熱路徑不受影響——
無狀態與可撤銷的衝突就消失了。

### 決策

| | Access token | Refresh token |
|---|---|---|
| 形式 | JWT（自包含） | 不透明隨機字串 |
| 有效期 | 15 分鐘 | 7 天 |
| 使用頻率 | 每個請求 | 每 15 分鐘一次 |
| 驗證 | 純 CPU，零遠端呼叫 | 查資料庫 |
| 可撤銷 | ❌ | ✅ |

**熱路徑的性質完全沒變**——仍然是純 CPU 驗證、零遠端呼叫，
原決策的核心論證（這是 JWT 能待在熱路徑上的唯一理由）依然成立。

撤銷的空窗從 2 小時縮短到最多 15 分鐘。若業務要求更短，
可以繼續調降 access token TTL，代價只是續期頻率上升——
**這是一個連續的旋鈕，而不是「有或沒有」的取捨**，這正是雙軌設計的價值。

### 輪替與重用偵測

每次續期都發新 token 並將舊的標記為已輪替。已輪替的 token 再度出現，
代表該憑證曾外洩——合法用戶端不會保留它。
此時無法分辨誰是竊取者，因此撤銷整條輪替鏈，逼雙方重新登入。

誤傷合法用戶端的代價是重登一次；放過的代價是攻擊者能無限期維持存取權。

### 開發用發證端點已移除

`DevTokenController` 不做任何身分驗證，任何人都能指定 userId 換到令牌。
它存在的唯一理由是「沒有別的方式能拿到令牌」——
有了真正的註冊登入，那個理由不再成立。

**臨時後門的正確處置是在其理由消失的當下移除，而不是靠設定旗標長期看管。**
每多留一天，就多一天被誤開到正式環境的機會。

### 新增的代價

- **多了一張 `refresh_token` 表。** 寫入量是「登入次數 × refresh 頻率」，需要定期清理（已實作 `RefreshTokenCleanupScheduler`）。已過期的紀錄保留 30 天供安全事件調查——立刻刪掉等於把線索一併刪掉。
- **撤銷必須走獨立交易。** 重用偵測的流程是「撤銷整條鏈 → 拋例外拒絕請求」，而拋例外會讓交易回滾、把撤銷一起還原。因此撤銷經由 `RefreshTokenRevoker`（`REQUIRES_NEW`）。**這個陷阱在單元測試中完全隱形**——mock 會顯示 `revokeFamily` 確實被呼叫了。
- **重用偵測會誤傷。** 使用者在網路不穩時重送續期請求，可能觸發撤銷而被迫重登。這是刻意接受的取捨：寧可誤傷也不放過。
- **重新評估的時機**：若誤傷的客訴頻率變得無法接受，可考慮加入寬限窗口（例如同一 token 在數秒內的重複請求視為網路重試而非重用）。但那會開出一個攻擊窗口，需要量化評估後才做。
