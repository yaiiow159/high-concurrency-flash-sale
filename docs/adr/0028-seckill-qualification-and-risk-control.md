# ADR-0028：搶購資格預檢與風險控管

- 狀態：已接受
- 日期：2026-09-07
- 相關：[ADR-0003](0003-lua-atomicity-over-distributed-lock.md)（熱路徑的原子性）、
  [ADR-0005](0005-jwt-resource-server-over-custom-filter.md)（JWT 待在熱路徑的理由）、
  [ADR-0023](0023-queue-depth-as-service-level.md)（入場控制）

---

## 背景

這個系統的削峰漏斗有四層：本機售罄標記 → 入場控制 → Redis Lua 扣減 → MQ。
每一層都在做同一件事：**讓注定失敗的請求以更低的成本被擋下**。

但它們擋的都是「來了之後」。真實的秒殺系統有一層更前面的：
**開賣之前就決定誰有資格來**。少了這一層，三種人與正常使用者付一樣的成本：

- 連網頁都不開的腳本——開賣瞬間直接打 API
- 一個人註冊五十個帳號，每個都來搶一份
- 剛被客服認定刷單、但令牌還沒過期的人

熱路徑上做不了這些判斷：查黑名單要讀資料庫，算「同 IP 幾個帳號」要讀 Redis，
而鐵則 2 明說熱路徑禁止新增遠端呼叫——JWT 能待在那裡的唯一理由是驗證純 CPU。

---

## 決策

### 1. 資格是一枚憑證，在冷路徑簽發、在熱路徑驗簽

開賣前 30 分鐘起，使用者可以「領取搶購資格」（`POST /seckill/activities/{id}/qualify`）。
這條路徑可以慢、可以讀資料庫：

| 檢查 | 讀什麼 |
|---|---|
| 驗證題答對 | 不讀——題目與到期時間簽在 token 裡 |
| 帳號未停權 | MySQL |
| 不在黑名單 | MySQL |
| 活動在領取窗口內 | Redis 快取 |
| 風險分數未過線 | Redis（同 IP／同裝置的帳號數） |

全部通過就簽一枚 HMAC 憑證：`userId.activityId.expiresAt.nonce.signature`。

熱路徑（`SeckillApplicationService.attempt`）只做三件純 CPU 的事：驗簽、比對人與活動、看到期。
**零遠端呼叫**——與 JWT 待在那裡的理由完全相同。

憑證活不過活動結束，最長 15 分鐘。太早領的話它會在開賣前就過期，所以領取窗口從開賣前 30 分鐘起。

### 2. 風險是加總的分數，不是任一命中就拒絕

單一訊號都有無辜的解釋：宿舍共用 IP、剛註冊就來搶、換了手機重新登入。
疊在一起才像機器人。四個訊號、四個權重、一條拒絕線（60）：

| 訊號 | 分數 |
|---|---|
| 帳號註冊不到 10 分鐘 | +30 |
| 同一 IP 十分鐘內超過 20 個帳號領資格 | +20 |
| 同一裝置超過 3 個帳號 | +40 |
| 同一人十分鐘內領超過 5 次 | +20 |

被拒的原因**記在 log，不回給使用者**——告訴他被哪一條擋下，等於教他怎麼繞。

IP 的權重刻意最低：沒有反向代理時 `X-Forwarded-For` 可以自填（會繞的人一定會繞），
而行動網路的 CGNAT 出口後面是成千上萬個真人（不會繞的人會被誤殺）。它只能當旁證。

訊號的 key 帶固定時間桶（`epoch / window`）：桶到點就換新的，計數才會真的歸零。
每次觀察都把同一個 key 的 TTL 推回去的話，只要流量不斷窗口就永遠不關，
被拒的人重試一次就多一分，永遠回不去。

訊號放 Redis 而不是 MySQL：它們只描述「最近十分鐘」，自動過期比排程清理便宜。

### 3. 黑名單與停權是兩件事

停權（[#72](https://github.com/yaiiow159/high-concurrency-flash-sale/pull/72)）是帳號層級的：不能登入、不能下任何單。
黑名單是**秒殺層級**的：仍可登入、逛、下一般訂單，只是拿不到搶購資格。

客服認定「這個人在刷秒殺」時，多數情況不需要把他整個帳號關掉——
他一般訂單的錢照收。兩者共用一個開關會讓客服在「放過刷單」與「趕走顧客」之間二選一。

### 4. 驗證題無狀態

開賣前一分鐘幾十萬人同時領題，題目若存 Redis 只是把尖峰往前搬。
所以題目（`a + b`）與到期時間一起簽在 token 裡，驗證時重算答案。

它擋的是「連網頁都不開的腳本」，不是決心破解的人——後者是風險評分的事。
答對的題目記一次性（Redis `SET NX`，一次往返）：不記的話，機器人解一次題
就能拿著同一個 token 在三分鐘內以任意速率打領資格——而那是全站最貴的端點。

---

## 被否決的方案

**在熱路徑查黑名單。** 一次 MySQL 主鍵讀約 1ms，在 1,400 QPS 下是每秒 1,400 次讀——
而 99.9% 的請求本來就注定失敗。那是為了擋 0.1% 的壞人，讓 100% 的人變慢。

**把停權／黑名單塞進 JWT claim。** JWT 15 分鐘才換一次，客服按下黑名單後最長 15 分鐘才生效；
而資格憑證本來就有自己的生命週期，把「秒殺資格」綁在「登入身分」上，兩者的更新節奏會互相牽制。

**在 MQ 消費端擋停權者。** 那裡拒絕的訂單已經扣了 Lua 庫存，要走補償退回——
把一個本來不該進來的請求放進來再吐出去，比在門口擋下貴得多。

**滑塊／圖形驗證碼。** 需要前端元件與圖片產生，而它們擋的與算術題是同一群人。
真要升級，換掉 `ChallengeCodec` 的實作即可，介面不動。

## 後果

- 熱路徑多一次 HMAC（約 2µs），零遠端呼叫。鐵則 2 的「上限」不變
- `require-qualification` 可以關（壓測與舊腳本用），但正式環境不該關——關掉等於拆掉最上面那一層
- 停權在秒殺路徑**仍然**只靠令牌過期收斂；黑名單才是即時的。要即時停掉一個人的秒殺，列黑名單
- 風險門檻是設定值，上線後要看 `seckill_qualification_total{result}` 調——
  拒絕比例過高是誤殺，過低是沒擋到
