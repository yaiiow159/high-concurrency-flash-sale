# ADR-0022：依類目篩選要包含子樹

- 狀態：已接受
- 日期：2026-09-05
- 相關：[ADR-0021](0021-keyset-pagination.md)（keyset 分頁）

---

## 背景

`findOnShelf` 的類目條件是 `p.categoryId = :categoryId`——**單一節點精確比對**。

在只有三個類目、商品直接掛在上面的開發資料裡，這是對的。
一旦類目變成一棵樹，它就錯了，而且錯得很安靜。

種入 225 個類目（1 個根 + 14 個二級 + 210 個三級）與 50,004 件商品之後：

| 點選的類目 | 層級 | API 回傳 | 該子樹實際商品數 |
|---|---|---|---|
| 3C 產品 | 1（根） | **0** | 50,004 |
| 子類目 1 | 2 | **0** | 3,571 |
| 子類目 1 / 細項 6 | 3（葉） | 100 | 238 |

只有**葉節點**查得到東西，因為商品只掛在葉節點上——
而那正是真實商品目錄的樣子。

### 前端把它放大成「每一個類目都是空的」

`categoryOptions` 只攤平兩層（根 + 直接子節點）：

```js
categories.value.flatMap((parent) => [
  { id: parent.categoryId, ... },
  ...parent.children.map((child) => ({ ... })),   // 到此為止
])
```

225 個類目裡只有 **15 個**出現在畫面上，而商品全部掛在那
210 個看不到的葉節點上。

兩件事疊起來的結果是：**使用者點得到的每一個類目，都回傳空頁面。**

單獨看，兩者都不像 bug。「篩選只比對單一節點」在一層的目錄下是正確的；
「只攤平兩層」在兩層的目錄下是正確的。
**它們各自的假設都沒寫下來，於是也沒有人發現假設已經不成立。**

---

## 決策

### 1. 篩選一個類目，等於篩選它的整棵子樹

點「3C 產品」要看到 3C 底下的全部商品，這是所有電商的行為，
不需要為它找理由。要決定的是**子孫集合在哪裡算出來**。

### 2. 在應用層從類目樹算出子孫，不加 schema

候選方案：

| 方案 | 代價 |
|---|---|
| 查詢時用遞迴 CTE | 每次列表查詢多一次遞迴，而類目幾乎不變 |
| 物化路徑（`path` 欄位） | 多一個必須在新增／搬移時維護的欄位 |
| 閉包表 | 多一張表與一整套維護邏輯 |
| **應用層展開**（採用） | 類目樹要在記憶體裡 |

選最後一個，理由是**這個決定已經做過了**。`CategoryView.buildTree`
的註解寫著：

> 在應用層組樹而非讓資料庫做遞迴查詢：類目總數以千為上限，
> 一次全撈再在記憶體裡組，比 N 次遞迴查詢快得多，程式也好讀得多。

同一棵樹、同一個規模、同一個理由。子孫展開跟著它走，
而不是為了同一棵樹再引入第二套機制。

物化路徑與閉包表都需要在**寫入路徑**維護一個不變式，
而那個不變式壞掉的症狀是「某些商品從此搜不到」——
安靜、難查、而且要等到有人抱怨才會發現。
在類目只有幾百個的規模下，為了省一次記憶體遍歷而買下這種風險並不划算。

### 3. 子樹涵蓋全部類目時，直接不加條件

點根類目等於「全部商品」。此時展開出來的 `IN (...)` 會包含每一個類目 ID，
那是一個沒有作用卻很貴的條件——它會讓優化器捨棄主鍵反向掃描，
退回索引加排序，正好踩中 [ADR-0021](0021-keyset-pagination.md) 要避開的那個懸崖。

因此：**展開後若涵蓋所有類目，就不下這個條件。**

### 4. 前端逐層展開，而不是一次攤平整棵樹

`buildTree` 本來就回傳完整的三層，是前端只讀了兩層。

**第一版改成完整攤平，那是錯的。** 225 個類目一次全列出來之後，
類目清單把商品格整個擠出畫面——使用者要捲過一整頁的類目
才看得到第一件商品。攤平修好了「點不到」，卻換來「找不到」。

改成只顯示**根類目 + 目前選取路徑上每一層的子類目**：
沒選時只有根，逐層點下去逐層展開，畫面上最多幾十個而不是 225 個。

**不需要額外的展開狀態**——選了哪個類目本來就在網址上，
展開到哪一層由它決定。這也讓深連結自動正確：
貼一個第三層類目的網址過去，路徑上每一層都會是展開的。

---

## 什麼時候該換掉這個方案

寫下來，才不會等到出事才想起：

- **類目數量進入五位數**。`IN (...)` 的參數量會開始讓查詢計畫變差，
  屆時應該換成物化路徑
- **類目需要頻繁搬移**。目前它幾乎不變；若變成日常操作，
  記憶體裡那棵樹的快取失效會變成新的問題來源

---

## 後果

**好的：**

- 每一個類目都點得到東西，包含中間層
- 沒有 migration、沒有新的寫入路徑不變式

**要付出的：**

- **查詢帶著一個最多數百個 ID 的 `IN` 清單**。在目前規模下沒有問題，
  但它是上面那條「五位數就要換」的原因
- **類目樹必須讀得到**。列表查詢因此依賴類目資料，
  這個相依原本不存在
