# ADR-0016：會員積分與等級

- 狀態：已接受
- 日期：2026-09-04
- 相關：[ADR-0013](0013-promotion-pricing-engine.md)（優惠計算引擎）、
  [ADR-0011](0011-refund-saga.md)（退款）、
  [ADR-0008](0008-dual-inventory-model.md)（庫存雙模型：流水與餘額）

---

## 背景

積分與等級看起來是兩張表加一支查詢，實際上它是這個系統裡
**第一個會被使用者主動嘗試套利的機制**。

庫存、訂單、退款的錯誤都是「系統做錯了」；
積分的錯誤是「使用者發現了一個可以重複做的動作」。
兩者需要的防禦不同：前者靠正確性，後者靠**讓套利在數學上不成立**。

具體會被試的路徑：

- 買了拿積分 → 退貨拿回錢 → 積分留著
- 買到升級 → 退貨 → 等級留著，之後用高倍率累積
- 同一筆訂單完成事件重放兩次 → 積分翻倍

---

## 決策

### 1. 積分是流水，餘額是快照

`point_transaction` 記每一次增減；`member_account.point_balance` 是可重建的快照。

這與庫存流水（ADR-0008）是同一個結構，理由也一樣：
**餘額回答「現在有多少」，流水回答「為什麼是這麼多」**，
而客服每天要回答的是後者。只存餘額的話，
「我的 500 點去哪了」這個問題永遠沒有答案。

流水存 `delta` 與 `balance_after` 兩個值。存 `balance_after` 是刻意的冗餘——
它讓每一列自我完備：稽核一列時不必把前面所有列加一遍就知道當時的餘額，
而「加一遍」在流水有幾萬列時是不可行的。

### 2. 餘額的更新是條件式增量 UPDATE

```sql
UPDATE member_account
   SET point_balance = point_balance + :delta, ...
 WHERE user_id = :userId
```

不是「讀出來、加、寫回去」。這是本專案第四次用同一個手法
（庫存扣減、券的核銷、評分聚合、積分）——**能壓成一句 SQL 的就不要用鎖**。

兌換時多一個守衛條件 `AND point_balance >= :cost`，
受影響列數為 0 就代表點數不足。與庫存扣減完全相同的形狀。

### 3. 冪等鍵是 `(user_id, reason, ref_no)`

訂單完成事件是至少一次投遞，重放是常態不是異常。
少了這個唯一索引，一次重放就是一次免費的積分。

**這道防線在資料庫，不在應用層。** 兩個並行的重放會同時通過任何
Java 端的「查過沒有」檢查——與訂單的 `request_id`、
評價的 `(order_no, sku_id)` 同一個角色。

### 4. 等級用「累計實付」而不是「積分餘額」

用餘額算等級會產生一個把整個機制反過來的激勵：
**使用者一花積分就降級**——而花積分正是我們希望他做的事。

因此等級由 `cumulative_spend` 決定，而積分餘額只是一種可花用的資產。
兩者從同一個事件更新，但語意完全不同：
一個是「你買了多少」（單調累積的事實），一個是「你還剩多少」（會增會減的餘額）。

| 等級 | 累計實付門檻 | 積分回饋倍率 |
|---|---|---|
| BRONZE | 0 | 1.0× |
| SILVER | 10,000 | 1.2× |
| GOLD | 50,000 | 1.5× |
| PLATINUM | 200,000 | 2.0× |

**等級必須做點什麼，否則它只是一個徽章。** 倍率是最便宜也最直接的作用，
而且它讓「升級」這件事有一個使用者算得出來的價值。

### 5. 積分在訂單「完成」時入帳，退款時按比例收回

入帳點是 `order.completed`（已送達），不是付款——
付款後到送達之間訂單還可能被取消，那段時間發積分只會製造要回收的債。

退款時扣回，而且**按比例**：部分退貨只收回那一部分。
比例的基準是**流水裡那一筆原始入帳**，不是重算一次——
重算會用到當下的等級倍率，而使用者可能在這期間升級了，
於是「退一半的貨」會收回比當初給的還多的積分。

`cumulative_spend` 同樣扣回。不扣的話「買了再退」就能免費升級，
而等級決定倍率——那是可以無限重複的套利。
**能被套利的忠誠度機制沒有意義。**

### 6. 餘額允許為負

沒有 `CHECK (point_balance >= 0)`。

原因是退款**絕對不能失敗**。使用者用積分換了券、然後退貨，
此時扣回會讓餘額變成負的——而那正是事實：他欠這些點。
加上 CHECK 的話，退款交易會在資料庫層爆掉，
結果是「錢退不了，因為積分不夠扣」——一個沒有人能理解的錯誤。

把餘額夾到 0 更糟：那讓套利成功，而且是靜悄悄地成功。

負餘額的使用者要先把它補回正的才能再兌換
（兌換的守衛條件 `point_balance >= cost` 自然涵蓋這件事）。

### 7. 積分的用途是「兌換優惠券」，不是直接折抵訂單

這是本 ADR 最重要的取捨。

直接折抵看起來更直覺，但它會讓**退款變成兩種資產的組合**：
使用者付了 900 元 + 100 點，全額退貨時要退 900 元「加」100 點。
而現在的退款路徑（ADR-0011）只認得錢——做一半的結果是
「錢退了、積分沒退」，一個安靜的黑洞。

換成兌換優惠券之後，這個問題消失了：點數換成券的那一刻，
它就是一張券，之後的行為與其他優惠完全一樣，退款路徑一行都不必改。

代價是多一步。但那一步換到的是「不必重新設計退款」，很划算。

---

## 不做的事

- **積分直接折抵訂單**。理由見決策 7——它要求退款支援多資產，
  那是一次獨立的改動
- **積分過期**。真實電商幾乎都有，而它會把消費順序變成一個
  先進先出的問題（先扣快過期的），流水結構要跟著改。
  值得單獨做一次
- **等級的降級寬限期**。真實電商多半用「年度累計」或「保級期」，
  避免使用者因為一次退貨就掉級。那需要時間窗口的概念，
  而目前的 `cumulative_spend` 是終身累計
- **會員專屬價格**。它會讓價格依身分而變，而目前
  「價格一律由目錄決定」是一條很乾淨的規則，值得多留一陣子
- **積分贈送、生日禮、簽到**。都是行銷活動，屬於 Promotion 的範圍

---

## 後果

**好的：**

- 積分有完整的流水，客服回答得了「我的點去哪了」
- 三種套利路徑都在數學上不成立：重放被唯一索引擋下、
  退貨會收回積分與累計消費、負餘額擋住再次兌換
- 併發安全靠一句 SQL，沒有引入新的協調機制

**要付出的：**

- 多兩張表，而 `point_transaction` 是**只增不刪**的，會一直長。
  需要歸檔策略（目前沒有）
- 等級是終身累計，沒有降級寬限期——一次大額退貨會讓人掉級，
  而真實電商多半用年度窗口避免這件事
- 積分要多一步才用得掉（先換券）。這是決策 7 的代價
- **`member_account` 與流水之間可能不同步**。兩者在同一個交易內更新，
  正常路徑不會分岔；但若有人繞過 `MembershipService` 直接寫流水，餘額就會失準。
  **已補上對帳**（`GET /api/v1/admin/inventory/reconciliation/points`）。
  只讀不修——偏差分不出是「流水漏寫」還是「有人改了餘額」，
  而兩者的正確修法相反
