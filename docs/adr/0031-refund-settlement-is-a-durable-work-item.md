# ADR-0031：退款的送達由持久化工作項保證，不由佇列重試保證

- 狀態：已接受
- 日期：2026-09-07
- 相關：[ADR-0011](0011-refund-saga.md)（退貨 Saga）、
  [ADR-0030](0030-publish-timeout-is-not-failure.md)（投遞逾時不是失敗）、
  [ADR-0023](0023-queue-depth-as-service-level.md)（佇列深度是服務水準）

---

## 背景

客服核可退款時，`ReturnRequest` 直接落到 `REFUNDED` 並發出 `refund.requested`，
真正的閘道退款則在消費端非同步執行。

問題是這兩件事之間沒有任何東西記得「錢還沒出去」：

```
1. ReturnService.refund：退貨單 → REFUNDED（commit）
2. 消費端 RefundExecutionService：呼叫金流閘道
3. 閘道暫時故障 → 重試 4 次、共 7.5 秒 → 進死信
4. DomainEventDeadLetterConsumer：log.error + 計數器 +1
5. 結束
```

第 4 步之後沒有第 5 步。**帳上寫著已退款，錢沒有送出去**，
而唯一的痕跡是一行 log 與一個沒有人盯的計數器。使用者會收到「退款已送出」的通知，
在退貨頁面上看到「已退款」，然後在幾天後打電話問錢在哪裡。

更糟的是這件事**查不出來**：`status = 'REFUNDED'` 的紀錄裡，
成功的與失敗的長得一模一樣。要找出漏掉的那幾筆，只能拿系統的紀錄
去跟金流商的對帳單逐筆比對。

### 為什麼不是「把重試次數調大就好」

因為消費端的重試是**阻塞式**的：它跑在 poll 迴圈裡，
一筆退款重試 5 分鐘就會擋住同一個分區後面所有人的退款，
而且會撞上 `max.poll.interval.ms`（預設 5 分鐘）被踢出消費組，觸發重平衡。

佇列的重試預算本來就只能是「短暫抖動」的緩衝，不可能是「閘道掛了兩小時」的答案。

---

## 決策

### 1. 「已核可」與「已到帳」是兩個狀態

`ReturnStatus` 新增 `REFUNDING`：

```
APPROVED ─┬─→ REFUNDING → REFUNDED
RECEIVED ─┘
```

- `startRefund` 落到 `REFUNDING` 並註冊事件——此刻錢還沒出去
- `settleRefund` 才是 `REFUNDED`，由閘道回覆成功後呼叫

這與 `PaymentStatus.REFUND_PENDING` 是同一個形狀：**當現實與帳目可能不同步時，
帳目要有一個格子承認這件事**，而不是先寫上樂觀的結果。

`REFUNDING` 沒有往「失敗」的轉移。已核可的退款只能往前推到成功——
買家的貨已經退了，回頭當作沒發生的話他既沒貨也沒錢。

### 2. 資料庫是工作項，佇列只是加速器

`RefundSettlementScheduler` 每分鐘掃 `status = 'REFUNDING'` 且發起超過寬限期的單，
直接呼叫 `RefundExecutionUseCase`。

因此訊息進不進死信都不影響最終結果：訊息路徑是**快車道**（正常情況下幾秒內完成），
排程是**保證**（不受任何重試預算限制，閘道恢復後自然推完）。

寬限期（預設 5 分鐘）必須明顯長於消費端的重試預算，
否則排程會與還在重試的消費端同時對同一筆退款呼叫閘道。閘道的冪等鍵擋得住，
但那是最後一道防線，不該被當成第一道用。

### 3. 重試預算依「失敗了要靠什麼救回來」分檔，不依重要性

先前所有消費端共用一份 7.5 秒的預算。改成兩檔：

| 檔位 | 預算 | 給誰 | 為什麼 |
|---|---|---|---|
| 快 | 約 7.5 秒 | 建單、退款、通知、積分 | 另有救援管道；久留只會擋住後面的人 |
| 慢 | 約 90 秒 | 搜尋索引、圖片衍生檔 | 失敗後只能人工重建，而 topic 量小、卡著沒有代價 |

慢檔的上限刻意壓在 `max.poll.interval.ms` 之下。
**退款屬於快檔**——它現在有排程了，在佇列裡久留反而是壞事。

實作上慢檔的錯誤處理器**刻意不註冊成 Bean**：Spring Boot 用
`ObjectProvider.getIfUnique()` 把 `CommonErrorHandler` 裝到預設容器上，
多一個同型別的 Bean 會讓它解析不到唯一候選，於是預設容器安靜地退回沒有死信的行為。

### 4. 重放整個 topic 不可以把錢再退一次

`auto-offset-reset` 是 `earliest`，新的 consumer group 第一次上線會重放整個 topic
（[鐵則 4](../../CLAUDE.md)）。先前擋住重複退款的只有閘道的冪等鍵——
那是外部系統的行為，不是我們的不變式。

現在 `RefundExecutionService` 第一件事就是檢查退貨單還在不在 `REFUNDING`，
不在就直接返回。這個判斷來自我們自己的資料庫。

### 5. 看得見

新增 `refund_awaiting_settlement_total` 量測 `REFUNDING` 的筆數。

短暫非 0 是正常的（閘道呼叫需要時間），**持續非 0 才是訊號**：
補送排程推不動它。告警設在持續 10 分鐘。

前端的退貨進度條也跟著拆成「退款已發起」與「退款已送出」兩步。
併成一步的話，閘道卡住時使用者看到的是一個永遠不亮的步驟，
而畫面上沒有任何東西說明它為什麼不亮。

---

## 被否決的方案

**把死信寫進資料表，做一個通用的重送後台。** 方向對，但它把「保證退款送達」
變成一件需要有人去按按鈕的事。退款不該等人；而且通用重送要面對
「哪些事件重放是安全的」這個問題——那個答案每個事件型別都不一樣
（寄信、扣款、呼叫外部 API 全都不能無腦重放）。針對退款做一個
可以被證明安全的專屬路徑，比做一個什麼都能重放的按鈕更誠實。

**改用非阻塞重試（`@RetryableTopic`）。** 它解決了阻塞的問題，
但重試次數仍然是有限的，最終還是會進死信——只是把 7.5 秒換成幾小時。
持久化工作項沒有上限，而且它同時給了「哪些退款卡住了」這個查詢。

**在消費端把錢退不出去的單改成失敗狀態。** 這會讓退貨單回到可撤回的狀態，
而買家的貨已經寄回來了。與[鐵則 8-1](../../CLAUDE.md)（收款成功絕不可被改寫成失敗）
同一個立場：已經發生的事實不可以因為下游失敗就被改寫。

## 後果

- 退貨單多一個狀態，前端與後台都要顯示它。這是刻意的：
  「錢還在路上」對使用者與客服都是有意義的資訊
- `refunded_at` 的語意收緊成「錢確實出去的時間」，發起時間另存 `refund_started_at`。
  既有資料以 `refunded_at` 回填發起時間——留 NULL 的話補送排程會把它們全部重推一次
- 退款通知仍然發在 `refund.requested` 上，也就是**發起**的當下。
  閘道卡住時使用者會提早收到「退款已送出」——這一點沒有解決，
  要解決得再引入一個 `refund.settled` 事件，而那會帶來一個新的消費端與新的冪等問題
- 補送排程與退款消費端可能同時對同一筆呼叫閘道（寬限期只是把窗口縮小，沒有消除）。
  依靠的是閘道以退貨單號為冪等鍵——這是**外部系統的保證**，
  換金流商時必須重新確認這件事
