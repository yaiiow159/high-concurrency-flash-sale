# ADR-0007：訂單聚合根重構為多品項

**狀態**：已採納
**日期**：2026-09-01
**相關**：[ADR-0006](0006-dual-order-channels.md)（雙下單通道）、[ADR-0004](0004-outbox-saga-over-seata.md)（Outbox）

## 脈絡

現在的 `SeckillOrder` 是**單品項**模型：

```java
private final Long activityId;   // 單一活動
private final int quantity;      // 單一數量
private final BigDecimal amount; // 單一金額
```

購物車結帳（一次買 3 件不同商品）根本寫不進去。這是擴充成電商平台的
**阻斷性缺口**——不是「不夠好」，是「做不到」。

而訂單是整個系統的樞紐：付款、履約、退款、對帳、報表全都掛在它上面。
**這次重構的成本會隨掛在訂單上的下游數量指數上升**，越晚做越痛。

## 選項

### A. 新增獨立的 `NormalOrder` 型別，與 `SeckillOrder` 並存

每個下游都要處理兩種型別：付款要分支、退款要分支、對帳要 union、
「我的訂單」查詢要合併兩個來源。**每新增一個下游，就多一處分支。**

這是把一次重構的成本，換成永久的複雜度稅。

### B. 在 `SeckillOrder` 上加 `items` 欄位（漸進）

舊的 `quantity` / `amount` 與新的 `items` 並存，兩個真實來源。
遲早會出現「`amount` 是 500 但 items 加總是 480」的資料，
而且沒有任何機制會告訴你。

### C. 一般訂單用另一張表

同 A 的問題，而且更糟：訂單號可能跨表衝突，
使用者的訂單列表要 union 兩張結構不同的表。

### D. 重構為 `Order` + `OrderLine`，秒殺訂單是「單行 Order」（本方案）

一種型別、一張表、一個狀態機。秒殺是**特例**，不是另一種東西。

## 決策

```
Order（聚合根）
 ├── orderNo, userId, channel, status
 ├── totalAmount, discountAmount, shippingFee, payableAmount
 ├── addressSnapshot
 └── List<OrderLine>
      └── skuId, skuSnapshot, unitPrice, quantity, subtotal
```

**秒殺訂單 = 只有一條 line 的 Order。** 沒有子類別、沒有多型。

### 金額存下來，而非每次計算

金額欄位是 lines 的加總，理論上可以每次查詢時算。但這裡刻意**反正規化存下來**：

**理由是訂單金額在建立後不可變。** 訂單一旦成立，lines 不會增減、單價不會變
——因此「儲存值與計算值不一致」的風險為零。

部分退款不會修改原訂單金額，而是產生獨立的退款紀錄。
這條規則必須守住，否則上面的推理就不成立，
反正規化也就從最佳化變成了資料完整性風險。

金額由聚合根在建立時計算並封裝，**不開放 setter**。

### `request_id` 唯一索引必須完整搬過去

現有 `seckill_order` 上的 `uk_request_id` 是**防重複下單的最後一道防線**
（見 CLAUDE.md 的三層冪等）。Redis 冪等與 MQ 冪等都可能失效，
唯有這條約束是無條件成立的。

新表必須帶著它。**遷移過程中任何一刻都不能沒有這個約束。**

### 新增 `order_state_log`

```
order_state_log
  id, order_id, from_status, to_status, reason, operator, created_at
```

訂單狀態爭議（「我明明付款了怎麼變取消」）是電商客訴的主要來源。
沒有軌跡就只能查日誌，而日誌會過期、會被輪替、也不保證撈得到。

### 狀態機擴充

沿用現有的 `ALLOWED_TRANSITIONS` 表設計——合法轉移集中宣告在一處，
新增狀態只需改一張表，而非散落各處的 if-else。

```
CREATED → PENDING_PAYMENT → PAID → SHIPPED → COMPLETED
              │               │        │
              ▼               ▼        ▼
          CANCELLED       REFUNDING ← RETURNING
              ▲               │
           FAILED             ▼
                          REFUNDED
```

## 遷移策略

**這是本專案至今最大的一次重構。不要一次性替換。**

現有的 70 支測試是這次遷移最重要的安全網——**遷移期間不刪任何一支**。

### 程式碼

```
1. 新增 Order / OrderLine 模型與測試（舊模型完全不動）
2. SeckillOrder.create() 改為委派給 Order 的單行建構捷徑
   → 此時舊測試應全部仍然綠燈，這是遷移正確的證據
3. 逐一遷移下游：MQ 消費端 → 對帳 → Outbox 事件 → 查詢
4. 全綠後才刪除舊模型與舊測試
```

第 2 步是關鍵檢查點：**如果讓 `SeckillOrder` 委派給 `Order` 之後
舊測試就紅了，代表新模型的語意與舊模型不等價**，要先解決這件事，
不可以順手改測試讓它變綠。

### 資料庫

分成三個獨立的 migration，**中間可以停下來驗證**：

| Migration | 內容 | 可否回頭 |
|---|---|---|
| `V3` | 建立 `orders` / `order_line` / `order_state_log` | 可，新表無人使用 |
| `V4` | 把 `seckill_order` 資料搬過去並比對筆數 | 可，舊表仍在 |
| `V5` | 移除 `seckill_order` | **不可逆，確認無誤後才執行** |

`V5` 建議與 `V4` 間隔至少一個發布週期。

> **實際執行時的調整**：建表與搬遷最後合併在 `V5` 一起上，
> 而移除舊表往後推到 `V14`——中間隔了九個發布週期而不是一個。
>
> 推遲不是拖延。舊表留著的期間，每一次「訂單資料好像怪怪的」都可以
> 直接對照原始資料查證，而那個能力在剛換模型的那幾週值好幾倍的成本。
> 真正該問的不是「隔多久」而是「還有沒有人需要它」——
> 確認唯一還提到它的地方只剩 `V1` 與 `V5` 這兩份歷史遷移本身之後才動手。

### Outbox 事件的版本相容（最容易漏掉的一環）

部署當下，Kafka 佇列裡還躺著**舊格式**的訂單事件。
新版消費端若只認得新格式，那些訊息會全部進 DLQ。

對策：事件加 `schemaVersion` 欄位，消費端在過渡期同時支援兩版，
確認佇列清空後才移除舊版分支。

這正是 [ADR-0004](0004-outbox-saga-over-seata.md) 所說「事件是跨行程契約，
欄位只增不改」的具體應用——只是這次連結構都要改，所以需要顯式版本標記。

## 代價

- **重構期間系統會有一段時間存在兩套模型。** 這是刻意的取捨：換取任何一步都能停下來驗證的能力。一次性替換雖然乾淨，但失敗時無法二分定位。
- **對帳邏輯要跟著改。** `sumActiveQuantity` 從單表查詢變成 join `order_line`，索引要重新評估。庫存對帳是防超賣的最後防線，這部分的測試不可放寬。
- **查詢效能特徵改變。** 訂單列表從單表變成一對多，需要留意 N+1。對策是列表頁只查 `orders`，明細才 join `order_line`。
- **重新評估的時機**：若日後出現「訂單行數量極大」的場景（例如 B2B 批量採購一張單上千行），聚合根一次載入所有 lines 會有記憶體壓力，屆時需要考慮分頁載入或把 line 拆成獨立聚合。目前的 C2C 場景（單筆數行到數十行）不需要。
