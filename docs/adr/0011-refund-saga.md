# ADR-0011：退款退貨作為獨立聚合根與第二個 Saga

- 狀態：已接受
- 日期：2026-09-03
- 相關：[ADR-0004](0004-outbox-saga-over-seata.md)（Outbox + Saga）、
  [ADR-0007](0007-multi-line-order-aggregate.md)（多品項訂單）、
  [ADR-0008](0008-dual-inventory-model.md)（庫存雙模型）

---

## 背景

`OrderStatus` 從一開始就把退款排除在訂單狀態機之外，註解寫著
「退款是另一條流程，會有自己的狀態」。這份 ADR 就是那條流程。

它是系統裡的**第二個 Saga**，而且比下單補償難：

| | 下單補償 | 退款 |
|---|---|---|
| 要還原的東西 | 只有庫存 | 錢**和**貨 |
| 觸發者 | 系統（逾時、DLQ） | 人（買家申請、客服核准） |
| 時間跨度 | 秒到分鐘 | 天（等貨寄回） |
| 粒度 | 整筆訂單 | 可能只退一行的一部分 |
| 重複執行的代價 | 多退庫存 → 少賣 | 多退錢 → **直接虧損** |

最後一列是整份設計的重心。冪等在下單那條路上是「避免超賣」，
在這裡是「避免把錢送出去兩次」——後者沒有對帳能事後補救。

付款端目前已有 `SUCCEEDED → REFUND_PENDING → REFUNDED`，
但那條路徑只服務一個競態：**錢收了但訂單已被逾時關單**。
它是系統自己發起的、必然全額的、沒有貨要處理的退款。
使用者發起的退貨完全不是同一件事。

---

## 決策

### 1. 退貨是獨立聚合根 `ReturnRequest`，不是訂單上的欄位

一張訂單在生命週期中可能產生**多張**退貨單（先退一件、兩週後再退另一件），
每張各自有審核與收貨的進度。把它壓成訂單上的欄位，
等於強迫「同時只能有一張退貨單」這個限制，而那個限制沒有業務理由。

退貨也用著另一套詞彙——申請、審核、寄回、驗收——
那是**售後**脈絡的語言，不是下單的語言。

`ReturnRequest` 引用訂單編號與訂單行，但**不反向修改訂單**。

### 2. 訂單狀態只增加 `REFUNDED`，且只在全額退完時進入

沿用 `OrderStatus` 已經寫下的判準：**只收錄「會改變買家能做什麼」的轉折**。

- ❌ 不加 `REFUNDING`。退款進行中，買家能做的事沒有改變——
  他仍然不能重複申請同一批商品，而擋住這件事的是退貨單而不是訂單狀態。
  加了它，訂單狀態會隨著退貨單的建立與完成來回翻動，
  那正是 `Shipment.FAILED` 被擋在訂單狀態機外的同一個理由
- ✅ 加 `REFUNDED`（終態）。全部退完之後，這張訂單不能再申請退貨、
  不能再出貨、也不該在列表上顯示「已完成」。那確實是一個里程碑

部分退款**不改變訂單狀態**。訂單留在 `COMPLETED`，
還沒退的那些行仍然可以再申請。

### 3. `REFUNDED` 的訂單仍然 `holdsStock() == true`

這條最反直覺，但寫錯會讓對帳誤報。

秒殺的第一條恆等式是
`Redis 餘量 + 進行中訂單數量 = 活動總量`。
退回的貨進的是**一般庫存**（見決策 4），Redis 餘量不會增加。
若 `REFUNDED` 不再算作佔用，等號左邊就少了那個數量，
對帳會報 `STOCK_LEAKED`——而實際上什麼都沒洩漏。

從活動的角度看：那一件**確實賣掉了**，只是後來被退回一般庫存池。
活動的配額從頭到尾就是被消耗掉的。

### 4. 退回的庫存一律進一般庫存，**絕不回秒殺池**

三個理由，任何一個單獨成立就足夠：

1. **活動可能早就結束並釋放過了。** 把量寫回 Redis 等於復活一個已釋放的活動——
   那正是 ADR-0008 明文禁止的事，也是實際發生過的超賣路徑
2. **Redis 的庫存鍵有 TTL。** 寫進一個會過期的鍵，那批貨會安靜消失
3. **配額是事前決定的。** 一件三天後才寄回的商品，
   沒有理由用秒殺價賣給下一個剛好在線的人

因此退貨只產生一筆 `RESTORE` 流水（`availableDelta = +q`），
`allocated` 完全不動。

### 5. 錢與貨在不同時間點移動，流程必須分成兩步

| 訂單狀態 | 需要寄回嗎 | 流程 |
|---|---|---|
| `PAID`（未出貨） | 否——貨還在倉庫 | 核准後直接退款並回補庫存 |
| `SHIPPED` / `COMPLETED` | 是 | 核准 → 等寄回 → 驗收 → 退款並回補 |

```
REQUESTED ──approve()──▶ APPROVED ──receive()──▶ RECEIVED ──refund()──▶ REFUNDED (終態)
    │                        │                                              ▲
    │                        └───────── 免寄回時直接退款 ───────────────────┘
    │
    ├──reject()──▶ REJECTED  (終態)
    └──cancel()──▶ CANCELLED (終態，買家自行撤回)
```

**驗收時才決定庫存是否回補。** 收到的貨若不可再售（毀損、缺件），
`available` 不增加，也**不補任何流水**——
原本的 `DEDUCT` 已經記過那批貨離開了，報廢只是它真的沒回來。
多補一筆反而會讓帳目對不上。「為什麼沒回補」記在退貨單上，
那是它該待的地方。

### 6. 退款金額的上限守在 `Payment` 聚合根，不在退貨流程裡算

`Payment` 增加 `refundedAmount`，不變式為 `refundedAmount ≤ amount`。

把上限放在退貨流程裡，意味著每條會退錢的路徑都要自己記得檢查——
而系統裡已經有兩條（使用者退貨、`PaymentRefundScheduler` 的競態補償），
未來只會更多。放進聚合根，繞不過去。

`PaymentStatus` 增加 `PARTIALLY_REFUNDED`。
不用「維持 SUCCEEDED，看金額就知道」是因為
`moneyReceived()`／`requiresAttention()` 已經證明這個列舉會被拿來做判斷，
而一個「退了一半卻說收款成功」的狀態遲早會餵錯答案給某個判斷。

### 7. 防重複退款是三層——比照第 4 條鐵則

| 層級 | 機制 | 擋掉什麼 |
|---|---|---|
| 退貨單 | 狀態機 `RECEIVED → REFUNDED` 單向 | 同一張單重複送出退款 |
| 訂單行 | 累計已退數量 + 本次 ≤ 原始數量 | 對同一批商品開兩張退貨單 |
| 付款 | 累計退款金額 ≤ 已收金額（樂觀鎖） | 前兩層都被繞過時的最後一道 |

第三層之所以必要：前兩層都在「退貨」這個脈絡裡，
而 `PaymentRefundScheduler` 走的是另一條路，看不到退貨單。

### 8. 實際呼叫金流走 Outbox，不在交易裡直接打

比照 ADR-0004。退貨單轉入 `REFUNDED` 的交易裡只寫 outbox 事件，
消費端負責呼叫金流。理由與訂單建立完全相同：
遠端呼叫留在交易裡，會把資料庫交易的存活時間綁在對方的回應時間上，
而逾時的結果是「不知道成功了沒」——退款這條路上，
那個不確定性等於「不知道錢送出去了沒」。

消費端**必須冪等**（Outbox 是至少一次語意）。

---

## 不做的事

- **自訂金額退款**。退款金額一律由訂單行快照的單價 × 退貨數量算出。
  容許客服輸入任意金額，「累計 ≤ 已付」以外就沒有任何可驗證的依據了
- **運費退還的計算**。運費目前不在模型裡
- **真實金流串接**。維持模擬閘道（使用者明確要求延後）
- **退貨的物流追蹤**。買家寄回的包裹不建立 `Shipment`——
  那個聚合根的語意是「賣家出貨」，塞進反向物流會讓它兩邊都不像

---

## 後果

**好的：**

- 訂單聚合根沒有因為退款而長胖，狀態機只多一個終態
- 部分退款是自然結果而不是特例——退貨單本來就引用訂單行的子集
- 三層防重複與既有的三層冪等是同一套思路，讀過一邊就懂另一邊

**要付出的：**

- 多一個聚合根、多一張表、多一條 Saga 要維運
- 對帳要多考慮一種情況：`REFUNDED` 訂單在秒殺側仍佔用、在一般庫存側已回補。
  這件事只靠讀程式碼看不出來，因此寫成決策 3 並配上測試
- `PaymentStatus` 從 5 個狀態變成 6 個，轉移表多一條自我轉移
  （`PARTIALLY_REFUNDED → PARTIALLY_REFUNDED`，多次部分退款）
