# ADR-0021：商店的商品列表改用 keyset 分頁

- 狀態：已接受
- 日期：2026-09-05
- 相關：[ADR-0015](0015-operations-console.md)（營運後台）、
  [ADR-0020](0020-order-create-partition-key.md)（壓測找出的瓶頸）

---

## 背景

`GET /api/v1/catalog/products` 用 `page` + `size`，翻譯成
`LIMIT :size OFFSET :page * :size`。

在 4 件商品的開發資料上這是對的。在 50,004 件上不是。

壓測（50 併發 × 12 秒）：

| 情境 | QPS | p50 |
|---|---|---|
| 第一頁 | 1,278 | 71 ms |
| 隨機翻到第 0–99 頁 | 154 | 65 ms（但 p90 = 996 ms） |
| offset 40,000 | **44** | **1,056 ms** |

### 它不是平滑劣化，是執行計畫翻盤

```
-- OFFSET 0
key: PRIMARY          rows: 40      Extra: Using where; Backward index scan

-- OFFSET 40000
key: idx_product_status_category   rows: 24564
                      Extra: Using index; Using filesort
```

offset 淺的時候，MySQL 沿主鍵反向掃、看 40 列就湊滿一頁。
offset 深了以後，優化器改走 `(status, category_id)` 索引，
然後**對 24,564 列做 filesort**——每一次請求都重做一次。

「隨機翻頁」那一列的 p50 只有 65 ms 而 p90 卻是 996 ms，
正是因為同一組請求裡有些落在翻盤前、有些落在翻盤後。
**平均值在這裡是騙人的。**

---

## 決策

### 1. 商店的列表改用 keyset（seek）分頁

```sql
WHERE status = 'ON_SHELF' AND id < :cursor
ORDER BY id DESC
LIMIT :size
```

游標是**上一頁最後一筆的商品 ID**。因為排序鍵就是主鍵，
`id < :cursor` 直接把掃描起點推到該去的地方——
不掃過、也不排序前面那 4 萬列。每一頁的成本因此**與位置無關**。

回應改成信封：

```json
{ "items": [...], "nextCursor": 49872, "hasMore": true }
```

`nextCursor` 由伺服器給，前端只負責原樣送回。
**不讓前端自己算**——它得知道排序鍵是什麼、方向是哪邊，
而那是伺服器的實作細節，洩漏出去之後排序規則就再也改不動了。

### 2. 用 `LIMIT size + 1` 判斷還有沒有下一頁

多取一筆，回傳前砍掉。這樣不必為了 `hasMore` 再打一次
`COUNT(*)`——在 5 萬列上那個 count 比查詢本身還貴，
而且它只是為了決定一個布林值。

**不回傳總筆數。** 商店列表不需要「共 2,500 頁」這個資訊，
而它要付的代價是每頁一次全表 count。

### 3. 游標無效時當作第一頁，不報錯

游標是不透明的字串，使用者可能改網址、也可能貼一個舊連結。
商品被下架之後，指向它的游標仍然是一個合法的 ID——
`id < 那個值` 依然成立，只是那一筆不會出現。這是對的行為，不需要處理。

真正無法解析的游標（非數字）回第一頁而不是 400：
**逛商品列表這件事不該因為網址被改壞而失敗。**

### 4. 後台維持 offset 分頁

`GET /api/v1/admin/products` 不動。理由不是「後台不重要」，
而是**兩者的存取方式本質不同**：

- 商店是往下捲，只會問「再給我 20 筆」——keyset 完全吻合
- 後台是一張表格，維運要能**直接跳到第 N 頁**，而 keyset 做不到
  跳頁：它只知道「上一頁的最後一筆」，不知道第 500 頁從哪裡開始

後台的使用者只有幾個人，而且都會先用狀態篩選（ADR-0015 決策 4
已經記過這個取捨）。要改的話應該連 UX 一起改成無限捲動，
而那是一個產品決策，不是這份 ADR 的範圍。

---

## 不做的事

- **不保留 `page` 參數做相容**。同時支援兩種分頁，等於保留那條會 filesort
  的路徑，然後期待沒有人走它。已知唯一的呼叫端是自家前端，一起改
- **不做「上一頁」**。往回翻需要反向游標（`id > :cursor` 配 `ASC` 再倒序），
  而商店的互動是往下捲、沒有上一頁按鈕。真的要做時再加
- **不換排序鍵**。目前是 `id DESC`（近似「最新上架」）。
  若之後要支援「依價格排序」，keyset 的游標必須是
  `(價格, id)` 複合值——單一欄位不足以定位，因為價格會重複。
  那時要改的是游標的編碼，不是分頁的機制

---

## 後果

**好的：**

- 翻到第幾頁都一樣快，`filesort` 的懸崖消失
- 順帶修掉一個沒人注意的缺陷：前端**根本沒有分頁 UI**，
  50,004 件商品只看得到最前面 20 件。加了游標才有辦法往下捲

**要付出的：**

- **對外契約改變**，回應從陣列變成信封。前端要跟著改
- **無法跳頁**。商店沒有這個需求，但這是 keyset 換來效能的代價，
  不是一個可以之後補上的功能
- **游標與排序鍵綁死**。換排序方式就要換游標的內容，
  這件事必須在加「依價格／評分排序」時一起想，不能事後補
