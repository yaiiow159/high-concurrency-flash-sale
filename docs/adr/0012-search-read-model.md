# ADR-0012：搜尋讀模型與最終一致窗口

- 狀態：已接受
- 日期：2026-09-04
- 相關：[ADR-0004](0004-outbox-saga-over-seata.md)（Outbox）、
  [ADR-0002](0002-stock-in-redis-not-database.md)（庫存不在資料庫）、
  [ADR-0006](0006-dual-order-channels.md)（雙通道）

---

## 背景

目前的商品查詢只有「依類目列出」與「依 ID 取單一商品」。
使用者想找「256G 黑色的手機」時，系統給不出答案。

加上搜尋會引入這個專案的**第一個讀模型**——一份與寫入端分開、
內容由事件非同步同步過去、且**必然落後**的資料副本。
落後多久、哪些畫面可以吃這個落後、哪些絕對不行，是這份 ADR 的主題。

---

## 決策

### 1. 用 Elasticsearch，而理由不是規模

先講清楚：**以目前的資料量，MySQL 的全文檢索綽綽有餘。**
幾百個商品用 `LIKE` 都跑得動。所以這不是效能決策。

選 ES 是為了三件 MySQL 做不好的事：

| 需求 | MySQL | ES |
|---|---|---|
| 中文分詞 | `ngram` 勉強可用，「小米手機」搜不到「手機」以外的合理結果 | IK 或內建 CJK 分析器 |
| 相關性排序 | 只能自己拼 `ORDER BY`，權重寫死在 SQL 裡 | BM25，欄位可加權 |
| 分面統計（品牌、價格區間） | 每個面向一次 `GROUP BY`，面向一多就是 N 次掃描 | 一次查詢回全部 aggregation |

**若這三件事都不需要，就不該引入 ES。** 一個新的有狀態依賴要備份、
要監控、要處理腦裂，那個成本是持續的。這裡引入它是因為搜尋體驗
本來就是電商的核心功能之一，而上面三件事沒有一件是可選的。

### 2. 同步走既有 Outbox，不做雙寫

寫入商品時同時寫 MySQL 與 ES（雙寫）是最直覺的做法，也是最錯的：
兩個資源無法原子提交，ES 那一半失敗時 MySQL 已經 commit，
**兩邊從此分岔且沒有任何東西會發現**。

既有的 Outbox 已經解決了這個問題——業務資料與事件在同一個交易裡落庫，
再由中繼器投遞。搜尋索引只是多一個消費組，邊際成本接近零。

這也是為什麼 P4 才做搜尋而不是更早：**它的低成本完全建立在
Outbox 已經存在之上**。

### 3. ES 永遠不是真實來源，價格與庫存不從它讀

搜尋結果會顯示商品名、圖、**價格**。而 ES 的價格是幾秒前同步過去的。

規則是：

- ES 只回答「**哪些商品符合條件**」與「大致長怎樣」
- 使用者點進去之後，商品詳情從 Catalog 讀，**庫存從 Redis 讀**
- **結帳一律不碰 ES**

搜尋列表上顯示的價格允許短暫落後——那和 CDN 快取住的商品頁是同一種延遲，
使用者可以接受。**但拿它去結帳就是用舊價格收錢**，那是財務問題。

這條線和訂單的「快照 vs 引用」是同一個判準的另一面：
訂單要的是「當初成交多少錢」所以存快照；
搜尋要的是「現在買要多少錢」所以只能給連結，不能給承諾。

### 4. ES 故障時 fail-open，降級回資料庫

對照專案既有的降級規則：

| 元件 | 故障時 | 理由 |
|---|---|---|
| 庫存（Redis） | **fail-closed** | 放行等於無上限超賣 |
| 限流（Redis） | fail-open | 後面還有庫存這道關卡 |
| **搜尋（ES）** | **fail-open** | 搜不到只是體驗差，不會產生錯誤資料 |

ES 掛掉時退回資料庫的 `LIKE` 查詢，並在回應裡標記 `degraded`，
讓前端可以提示「搜尋結果可能不完整」。

**降級策略要看「這道防線失守會付出什麼代價」，不能一刀切**——
這是 CLAUDE.md 第 3 條鐵則的同一個原則。

### 5. 重建索引是必備能力，不是補救措施

三件事都會需要整份重建：mapping 改了（ES 不允許改既有欄位型別）、
索引損毀、以及事件在某段時間內漏掉。

因此：

- 索引名帶版本（`products_v1`），對外一律透過 **alias** `products` 存取
- 重建時寫進 `products_v2`，完成後原子切換 alias，舊索引保留一段時間可回退
- 重建的資料來源是 **MySQL**，不是舊索引——從舊索引複製會把既有的錯誤一起複製過去

**沒有重建能力的讀模型是不可維護的**：任何一次 mapping 變更都會變成停機。

### 6. 商品需要寫入路徑才有事件可發

Catalog 目前<b>沒有任何寫入端點</b>，商品是遷移種進去的。
沒有寫入就沒有領域事件，也就沒有東西可以驅動索引。

因此一併補上商品上下架（與活動上下架同一個形狀），
並讓它發出 `product.published` / `product.delisted` 事件。

這不是為了搜尋硬加的功能——營運後台本來就在 P4 的清單上，
只是搜尋讓它變成必須先做的那一個。

## 最終一致窗口

| 路徑 | 可容忍延遲 | 理由 |
|---|---|---|
| 搜尋結果的商品清單 | 數秒 | 新商品晚幾秒才搜得到，沒有人會發現 |
| 搜尋結果顯示的價格 | 數秒 | 與 CDN 快取住的商品頁同級 |
| 商品詳情頁 | **0** | 直接讀 Catalog |
| 庫存數字 | **0** | 直接讀 Redis |
| 結帳計價 | **0** | 完全不碰 ES |

窗口的實際大小 = Outbox 中繼間隔（1 秒）+ Kafka 投遞 + ES refresh interval。
ES 預設 refresh 是 1 秒，因此**典型延遲約 2~3 秒**。

刻意不把 ES 的 refresh 調成 `wait_for` 或 0：那會讓每次寫入都強制刷新，
把 ES 最重要的批次寫入優勢丟掉，換來的只是三秒變一秒。

## 不做的事

- **搜尋建議（autocomplete）與拼寫糾正**。它們需要另一套索引與流量資料，
  而且在沒有真實搜尋日誌之前調不出有意義的結果
- **個人化排序**。同上，需要行為資料
- **秒殺活動進搜尋**。活動是時間窗口內的短命實體，
  而索引的同步延遲正好落在活動開始的那幾秒——那是最不能落後的時刻。
  活動用既有的活動列表（多級快取）呈現

---

### 索引版本保留一代

重建走 alias 切換，舊索引<b>刻意保留</b>供回退——新索引出問題時把 alias
指回去就能救。但先前<b>沒有任何東西會刪掉它們</b>：每重建一次就留下
一份完整的商品索引副本，而重建是維運按得到的按鈕。

磁碟滿了的症狀是整個 Elasticsearch 進入唯讀，那時連「搜尋降級回資料庫」
都救不了寫入。

因此切換 alias 之後清掉過舊的版本，只留一代。順序不可調換：
先清再切的話，中間若切換失敗就變成「新索引還沒生效、舊索引已經沒了」——
唯一一種會讓搜尋完全消失的組合。

清理失敗<b>不影響重建結果</b>：重建已經成功、alias 已經切好，
而刪不掉一個舊索引是磁碟問題不是正確性問題。讓它把整次重建變成失敗，
會誘使維運再按一次——而那又多留一份。

---

## 後果

**好的：**

- 第一個讀模型，而且是靠既有的 Outbox 驅動，沒有引入新的一致性機制
- ES 掛掉不影響下單——搜尋是唯一依賴它的功能，而它 fail-open

**要付出的：**

- 多一個有狀態的依賴要維運
- 多一份資料要對帳。索引與資料庫可能分岔（漏事件、消費失敗），
  需要一個「索引筆數 vs 資料庫筆數」的檢查，比照既有的庫存對帳
- 商品從此有兩個查詢入口（Catalog 直查、搜尋），
  兩者的欄位若各自演化會讓前端看到不一致的商品資料
