# ADR-0006：雙下單通道，秒殺與一般下單分離

**狀態**：已採納
**日期**：2026-09-01
**相關**：[ADR-0002](0002-stock-in-redis-not-database.md)（庫存放 Redis）、[ADR-0007](0007-multi-line-order-aggregate.md)（訂單重構）、[ADR-0008](0008-dual-inventory-model.md)（庫存雙模型）

## 脈絡

現有系統只有一條下單路徑，而它的**每一個設計都建立在同一個前提上**：
流量極大、庫存極小、99.9% 的請求注定失敗。

| 設計 | 存在的理由 |
|------|-----------|
| 本機售罄標記 | 絕大多數請求會失敗，要在最便宜的地方擋掉 |
| 非同步 202 + 輪詢 | 把資料庫寫入完全移出請求鏈路 |
| 庫存放 Redis | 所有請求競爭同一行資料，DB 鎖會塌陷 |
| 熱路徑禁 DB | DB 是吞吐瓶頸 |

要擴充成電商平台，就必須支援一般下單。而一般下單的流量特徵**完全相反**：
流量正常、SKU 數以萬計、絕大多數請求會成功、領域規則複雜（優惠、稅、運費）、
使用者期待立即知道結果。

問題是：**一條通道還是兩條？**

## 選項

### A. 統一走秒殺通道（全部非同步）

| | |
|---|---|
| 優點 | 只有一條路徑要維護；削峰能力涵蓋全站 |
| 缺點 | 使用者按下「結帳」後要輪詢才知道買到沒；五萬個 SKU 不可能全部預熱進 Redis；多品項加優惠券的計算，Lua 寫不下也不該寫 |

「買一本書也要輪詢」是這個方案的必然結果，不是實作沒做好。

### B. 統一走同步通道（放棄削峰）

| | |
|---|---|
| 優點 | 簡單、一致、領域邏輯好寫 |
| 缺點 | 秒殺會直接塌陷。[ADR-0002](0002-stock-in-redis-not-database.md) 已論證資料庫悲觀鎖與樂觀鎖在單一熱點下的失敗模式 |

等於把已經解決的問題重新製造出來。

### C. 單一通道 + 策略模式切換

看起來是漂亮的折衷：一個 `PlaceOrderUseCase`，用 `ChannelStrategy` 決定同步或非同步。

**但它會失敗，因為差異不在「策略」而在「呼叫形狀」**：

```java
// 一般下單：回傳訂單本身
Order placeOrder(PlaceOrderCommand cmd);

// 秒殺下單：回傳受理憑證，訂單稍後才存在
SeckillTicket attempt(SeckillCommand cmd);
```

回傳型別不同、HTTP 狀態碼不同（201 vs 202）、
錯誤語意不同、前端流程不同。強行統一只會得到一個
「回傳 `Either<Order, Ticket>` 讓呼叫端自己判斷」的介面——
那不是抽象，那是把分支推給了每一個呼叫端。

### D. 雙通道，共用領域模型（本方案）

兩條獨立的 Use Case 與 API，共用底下的領域模型與所有下游流程。

## 決策

**採雙下單通道。**

```
                ┌──────────────────────────────────────┐
                │  共用：Identity · Catalog · Ordering   │
                │        Payment · Fulfillment · 事件    │
                └──────────────────┬───────────────────┘
                                   │
          ┌────────────────────────┴────────────────────────┐
          │            分岔點只有兩個                        │
          │      ① 庫存扣減機制  ② 訂單建立路徑              │
          └────────────────────────┬────────────────────────┘
                    ┌──────────────┴──────────────┐
        ┌───────────▼──────────┐      ┌───────────▼──────────┐
        │   一般下單通道        │      │   秒殺下單通道        │
        │   channel = NORMAL   │      │   channel = SECKILL  │
        ├──────────────────────┤      ├──────────────────────┤
        │ 同步、單一交易        │      │ 非同步、最終一致      │
        │ MySQL 樂觀鎖扣庫存    │      │ Redis Lua 原子扣減    │
        │ 201 + 訂單           │      │ 202 + 受理憑證        │
        │                      │      │                      │
        │ 目標：正確性與彈性    │      │ 目標：極致削峰        │
        └──────────────────────┘      └──────────────────────┘
```

### 明確的邊界

**共用**（必須是同一份程式碼）：

- `Order` 聚合根與 `OrderLine`（見 [ADR-0007](0007-multi-line-order-aggregate.md)）
- 訂單狀態機與狀態轉移規則
- 付款、履約、退款、通知
- 領域事件與 Outbox 投遞
- 商品、使用者、地址

**不共用**（刻意各自實作）：

- 庫存扣減機制（見 [ADR-0008](0008-dual-inventory-model.md)）
- 訂單建立路徑（同步交易 vs MQ 消費端）
- API 契約與錯誤語意
- 限流策略（秒殺需要更嚴格的單一使用者限流）

### `channel` 欄位的使用紀律

訂單表有 `channel` 欄位（`NORMAL` / `SECKILL`），但它的用途是
**追溯與報表**，不是控制流程。

```java
// ❌ 禁止：領域層依 channel 分支
if (order.channel() == SECKILL) { ... } else { ... }

// ✅ 差異放在建立路徑，聚合根本身不知道自己是哪個通道來的
```

一旦領域層開始依 `channel` 分支，就等於把兩條通道的差異
滲透進共用的部分——那正是這個決策要避免的事。

## 代價

- **兩條路徑各自要測。** 測試量增加，且「一般下單能買、秒殺不能買」這類單邊故障需要各自的迴歸測試。
- **有重複邏輯的風險。** 兩條路徑都要組裝訂單、都要驗證商品可售。對策是把共用部分抽成 `OrderFactory`，只讓「庫存怎麼扣」與「訂單何時落庫」兩件事分岔；發現第三處重複時，就是該檢討邊界是否切錯的訊號。
- **`channel` 欄位會誘使人寫分支。** 上面的紀律必須靠 code review 守住，ArchUnit 抓不到這種違規。
- **重新評估的時機**：若秒殺活動的流量降到與一般下單同一量級（例如商業模式改為常態小量限購而非大促搶購），兩條通道的差異就不再值得，應合併回同步通道並撤掉 Redis 庫存層——那也正是 [ADR-0002](0002-stock-in-redis-not-database.md) 預留的退出路徑。
